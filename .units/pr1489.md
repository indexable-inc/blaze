docs/driver.md step 3: `resolve_all` (blaze-engine) schedules crates on `blaze-graph` instead of walking a list in order. Before, a thread that started on a crate whose dependencies weren't resolved yet resolved them itself inside the query, one after the other. Now each crate is a `Names` node that runs once the crates it depends on are resolved, longest remaining path first.

- The per-crate work moved unchanged into `resolve_one`. The idle-thread helpers (`warm_impls`, `warm_files`) count every thread at work, so the helpers they add are only the cores no crate holds.
- tui's `Counting` progress and `crate_is(Resolving/Resolved)` are kept: each running node takes a free slot. The machine's own records aren't said, because `events::graph` already says these crates' nodes with the names the build view shows.
- `RootDatabase` is `Send` but not `Sync`, so each node clones its database from a shared one under a lock, as each spawned thread cloned it before.
- `resolve_all` returns an error if the graph fails; both callers use `?`.
