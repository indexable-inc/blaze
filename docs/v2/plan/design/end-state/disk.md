# Disk: the store, a blaze home, collection, sharing

Lane disk, 2026-11-12, read on `/Volumes/Projects/blaze-int-1112`. Every claim is **measured** (with its source), **read** (from code or a doc, not run) or **design**. Nothing here was built or run. `~/.cache/blaze` was not read; its numbers are the brief's.

## 1. What this area must do, and the invariant

- Keep every record (`key, reads, value`) of end-state.md once, findable by its own key in one page read, at a cost per small item near the item's own size.
- Own every byte under a home: each file is a store extent, a materialization of records, or a ring of fixed size.
- Keep the home under one budget without a pause and without a person running a command.
- Survive a crash at any IO step as "the store before or after the commit", never a wrong value.
- Let records travel (a release's std, a team's CI) as the same bytes the store holds, taken only on a trusted saying.

**The invariant (three clauses, one oracle each).** (a) *Closed*: every entry under a home is named by the home's table or is in trash; an entry nothing names is garbage, not "refused". (b) *Bounded*: at every commit, `held <= budget` or `collectable == 0`; a write that would break it waits for the collector inside a named span, and when nothing is collectable fails naming the roots that hold the most. (c) *Never wrong*: a get returns the bytes put under that key or a miss; a record a live root reaches is never forgotten; a build never finds a key and then misses it.

## 2. How the best systems do it

- **Nix** (`src/libstore/gc.cc`, `LocalStore::collectGarbage`; Dolstra, "The Purely Functional Software Deployment Model", ch. 5). Take: the store is closed (a path the database does not know is deleted, not kept), and roots are *pointers held from outside* (`gcroots/auto`: a link that points at a link in the user's tree; the root dies when the user's link does). Do not take: one directory a value and a SQLite row a path (at 10^7 small values that is the file system's metadata as the index), and collection only when asked.
- **git** (`packfile.c`, `midx.c`, `Documentation/gitformat-pack.txt`; `git repack --geometric`). Take two ideas: *the wire format is the disk format* (a fetched pack is renamed into place with its index, never re-put), and the multi-pack index kept as a geometric chain of immutable sorted runs, merged in the background. Do not take: delta chains (our values are read in place) and loose objects (a second form with a migration between them).
- **WiscKey / Bitcask / FASTER** (Lu et al., FAST '16; Sheehy & Smith 2010; Chandramouli et al., SIGMOD '18). Take: values in an append-only log that is never rewritten to keep order; only a small index is maintained. Do not take from RocksDB: values inside the LSM, a WAL beside the log, and sorted-order locality: our keys are BLAKE3 output, so key order has no locality; locality must come from *what was written together*.
- **Buck2** (`app/buck2_execute_impl/src/materializers/deferred.rs`, `clean_stale.rs`). Take: `buck-out` is a materialization of CAS digests tracked in a table (path, digest, last access), so every output is deletable at any time and re-placed from the store. Do not take: the table in SQLite beside the store (a second durable thing with its own crash story).
- **Relax** (`compiler/src/cache/collected.rs`, `base/src/gitstore.rs`). Take: one file is a whole store (objects, then an index, then a trailer; an interrupted append is cut on the next write; compaction when garbage is over half). Its 41 MB for a hello-world (measured, brief) is the size to beat. Do not take: no budget and no collector across programs (not in `KNOWN_GAPS.md` as done).

## 3. blaze today

**Shape (read).** A home (`blaze-manifest/src/home.rs:68-88`) is `v2/` (store, image, journal, profile, ledgers), `build/<name>-<id>/` a checkout, `sources/`; beside it `<machine>/std/<makers>/w-<writer>` (a second, shared store, `blaze-cas/src/peers.rs`, `blaze-cargo/src/serve.rs:159`) and `~/.blaze/toolchains` (`blaze-cargo/src/toolchain/own.rs:225`, outside any home). The store (`blaze-cas`, 7,962-line `lib.rs`): per-worker segments, packs up to 1 GiB, a SwissTable index file plus a levelled delta table, a head flipped once a commit, reads through the pool (`hot.rs`, `read.rs`).

**Measured (brief, 2026-11-12, owner's Mac).** Home 1,337 GB, disk at 2.4 GB free; the collector tracks 498 GB, sweeps 0 at full pressure while 1.1 TB over; about 860 GB (coord 577.9, backup 208.2, runner-blaze 70.1, workers 9.3) is in directories no collector lists; store 4.5 GB; 192 GB in two forgotten homes in `/private/tmp`. A copied store gave 0 misses in another checkout and home, 6.8 s against 23.8 s. bstd hello-world cold 72.6 s with nothing fetched. Records of rebuilt blazes: 2.2 GB a day (measured, docs/gc.md, lane disk-1111).

**Smells under rule 66.**
1. *Two mechanisms for one job, three times.* Two collectors, `blaze_gc::plan::Collector` (directories) and `blaze_cas::collect::Collector` (records), with two drivers (`serve/gc.rs`, `serve/collect.rs`), joined by one number (`serve/gc.rs:294` `holds`). Two forms of an item (`sets.rs` live, `sealed.rs` sealed) with a get that looks in three places (`sets.rs:30-32`), a cap of four sealed sets, and a third (`check_cache`'s pages). Three ways to share (`blaze-cas/src/remote.rs`, `blaze_global` bundles, `blaze-pack`), and a fourth store format for travel (manifest + body + spans, `blaze-pack/src/{manifest,spans,import}.rs`) whose import puts each record again.
2. *Keep is the default; collect is a list.* `blaze-gc/src/plan.rs:217` `Class` lists five kinds of thing; "the driver lists nothing else, so nothing else is ever collected". A build directory with no lease file or record is `Keep::Refused` forever (`fs.rs:459-470`, `fs.rs:542`); `Keep` has 13 reasons (`plan.rs:488`). The daemon's state is "never listed" (`lib.rs:22-24`). This is the measured 0 swept and 860 GB unowned.
3. *A loop that reports and does not act.* At the budget with nothing it may take, the store's collector says `OverBudget` and looks again in ten minutes (`blaze-cas/src/collect.rs:1701`), and the build gets a line at most hourly (`serve/collect.rs:262-263`); no writer is ever told no.
4. *Liveness by recency.* A record is kept by four use flags (`collect.rs:15-20`). Under level 1 a certified no-op reads one record, so the records an edit will need go unread for weeks and age out. Recency is the wrong root for a certificate design (design claim; not measured).
5. *Per-process and per-binary keys.* `std/<makers>` (a store per code identity); every record key covers its maker's code, so a rebuilt blaze reads none of the last one's; `w-<writer>` directories never collected alone (docs/gc.md "Not done yet").
6. *Cost per small item.* 96-byte header (`disk.rs:158`) + 64-byte index row (`index.rs:21`) + a 32-byte leaf entry: 170-290 bytes over a 16-200 byte value (read). The index is written whole every 65,536 records (`lib.rs:195`); a pin is read, sorted and rewritten whole per change (`collect.rs:1128-1160`); a period's scan walks every row.
7. *mmap and two loaders.* `Effect::Map` is still asked for the index and external files (`lib.rs:5373`, `5799`, `7396`); loads are `Thread` in the daemon and `Pumped` in every simulation (`hot.rs:14-26`), so the simulated path is not the shipped one.
8. *Retry.* IO is tried eight times before the store breaks (`lib.rs:209` `FAILURES_MOST`); a read at the pinned bound waits 50 ms at a time for 5 s (`read.rs:57-59`).
9. *IO mixed with logic.* `blaze-gc/src/fs.rs` (1,560 lines) scans, locks and renames with `std::fs`; only `plan.rs` is a core.
10. *Unbounded.* `sources/`, toolchains, `disk-stamps` (caches.md defect 4), ledgers moved aside (`serve/why/file.rs:37`), and whatever wrote the 208 GB backup: `lib.rs:122-125` says a store of another format is refused with no migration, and no code that makes a backup was found by search (unknown, question 7.6).

## 4. The end state (design)

**One sentence.** A home is one closed tree with one table of owners, one collector, one budget and one record format; everything in it is a store extent, a materialization the store can make again, or a fixed ring.

**4.1 The home table (ownership).** `<home>/HOME` is written when blaze creates the home, only in a directory that is empty or absent; a home without it is refused, naming it. The table is a store record chain named by the head. Classes, and there are no others:

| Class | What | Owner (root) | Made again by |
|---|---|---|---|
| extent | `store/x-<n>` packs, `store/i-<n>` index runs, `store/head` | the head | builds, or a fetch |
| placed | `build/<checkout id>/…`: every file is `(path, key, stamp)` in that checkout's placement record | the checkout root | `place` (clone) |
| ring | profile history, logs, the ledger: each a fixed byte cap stated in the table | the table row | not needed |
| trash | `.blaze-trash/` | nobody | — |

The image and journal are records (rule 51), not files. Fetched sources and toolchains are tree records in the store placed like outputs; `sources/`, `~/.blaze/toolchains` and `<machine>/std` stop existing as directories with rules of their own. A **checkout root** is Nix's indirect root: the record names the checkout's path and the id of `<checkout>/.blaze/root` (one small file blaze writes in the checkout); the root is live while that file exists with that id. A deleted or moved-away checkout is a dead root at the next scan, with no TTL to tune. A scratch home (an agent's, a test's) is registered in the user's one registry (`<user cache>/blaze/homes`, a ring) with a lease and a time to live; a home in the registry whose lease is free past its time is trash for any daemon of the user. At open and once an hour a worker lists the home's top two levels; an entry no table row names is renamed to trash and said by name and size. There is no `Refused`.

**4.2 One collector, tracing from roots.** Roots: each live checkout's last K request certificates (K=2 a request shape), named pins (`toolchain`, `bstd`, an imported pack's head), builds in flight. Every record frame carries `children`: the keys it keeps (a certificate → unit records; a unit record → its listing; a listing leaf → item records and outputs; a chunked output → chunks). Children are not reads: reads say when a record holds, children say what the next edit needs. A unit's listing is the prolly tree `sets.rs` already has (leaf ends chosen by the key, so an edit rewrites one leaf and the path). **Mark** runs on a worker from a cursor, memory one bit per index ordinal (10^7 records: 1.25 MB), never a set of keys. **Sweep** is what is built: a pack more than half dead is taken, its live records copied on, the head names it retired (`collect_take/copy/seal`). Placed files of a dead root and rings past their cap go the same turn. Recency orders *roots* only (which checkout's old certificate goes first under pressure); it never decides a record.

**4.3 Disk admission.** One measure, the analogue of rule 50: bytes the home holds on its volume as the kernel counts them (blocks, clones once: `ATTR_CMNEXT_PRIVATESIZE` on APFS, `FIEMAP` shared flags on Linux), and the volume's free bytes. `budget = min(absolute, share, held + free − floor)`. A commit reserves its bytes before its first write. `Collector` is a sans-IO state machine: `Under → Soft (≥80%: mark, compact between builds) → Hard (≥100%: the committing task waits in span "disk admission: collecting", bounded by one mark + sweep lap) → Full (lap done, still over: typed error naming the three largest roots and their bytes)`. No ten-minute look-again, no warning line as the mechanism.

**4.4 The record form: batches in extents, a chain of index runs.** A writer's commit appends one **batch**: `header (magic, kind table, count, dictionary id) | directory: count × (key 32, offset u32, len u32, kind u8, n_children u8…) sorted by key | children keys | values, 8-aligned`. A value of 64 KiB or more is page-aligned in a batch of its own; an output that is placed is an extent file of its own so `clonefile`/`FICLONE` shares its blocks. Per small item over its bytes: 32 + 9 in the directory, 16 in the index, about 60 bytes, in one form (today 170-290 live, 57 sealed). Integrity at rest is the CRC-32C per 4 KiB block that exists (`checks.rs`); a content hash per record is not stored (4.6 says what replaces it for travel).

**Index.** Each commit writes one immutable **run**: entries `(key[0..8], extent u16, offset u48)` sorted, plus a binary fuse filter of 9 bits a key (Graf & Lemire 2022) held in memory. Runs merge geometrically on a worker (ratio 4), so 10^7 keys are about 12 runs before a merge and 2-3 after; the head names the chain. A get: filters newest first (memory: 1.2 bytes a key), interpolate into the run (keys are uniform, so the page is computed, not searched), one pool page; then the batch directory page, compare the whole key, then the value's page. Two to three pages cold, zero syscalls warm. A miss reads nothing with probability 1 − 0.4% a run. Nothing is rewritten whole, ever; a commit's index cost is 16 bytes a new record. Runs are derivable from batch directories, so recovery scans directories past the head's indexed ends and never reads values.

**Why not the others.** An LSM of values: compaction rewrites values to keep an order that hashes do not have. One file a crate: 10^5 files at reth's scale, the file system as the index, and an unchanged item of a crate's next version is found only if the index is global anyway (rule 65: a crate is a container, and here the container is the batch). A B-tree updated in place through the pool (LeanStore): needs a WAL or copy-on-write for crash safety that append-and-flip does not.

**4.5 Durability.** Records are a cache: losable, never wrong. One barrier a commit (`F_BARRIERFSYNC`, `fdatasync`), covering batch, run and checks, then the head written whole; a new extent's directory entry is synced before a head names it (storemodel.md finding 2). The answer to a client never waits for the barrier (the 1,513 ms behind an fsync in `publish.rs:191` is the reason); the lag is bounded at 1 s or 64 MiB, and a crash loses at most that tail, which is made again. A head of a format this binary does not read: the store directory is renamed to trash and the build says so with its size, once (rule 26: never silently empty, never kept as a backup). An IO error fails the commit that met it, naming file and offset; no eight tries.

**4.6 Sharing.** **A pack is an extent**: the same bytes as `x-<n>` with its run, named by the BLAKE3 of the extent; `head` = signed `(scope, pin, [extent hash, len, run hash])`. Import is: read the head, check its signature against `packs.json` `trusted`, stream each extent verifying BLAKE3's tree as it arrives (`blaze-fetch/src/verified.rs` exists), rename into `store/`, name it in the head as a read-only layer with the pin as its root. No record is put again; removing a pin retires whole files. **Fetch on miss**: per configured source, the head's filters are fetched once (1.2 bytes a key); a miss that a filter passes is two range reads (run page, then the batch that holds the key, taken whole and verified by its subtree hash: a publisher's batch is a unit's records, which travel together). Static files only: a bucket, a share, or a peer's daemon serving its own extents read-only by signed request. **The trust rule, one sentence, kept from remote-cache.md**: a key is mapped to bytes only by a saying signed by a key the user listed, and bytes are taken only when they hash to what the saying names. Out of the box the list holds the release key compiled in (their option (a)); a team adds its CI's key; a laptop's key is listed only by a person who chooses to, and machine code is never taken unsigned. A dishonest listed signer is the remaining hole; rule 25 makes the mitigation cheap (rebuild a sampled unit, compare bytes, refuse the signer by name on a difference). **Prebuilt std** is then: the release publishes `toolchain` and `bstd` extents per scope; first use fetches them before any unit is planned.

**Rules.** 3: no `Refused`, no look-again, no IO retries; a miss is a cache's defined answer, a failed source is said once by name. 11: mark bits, filters and run builders live in the collecting or committing task's frame; the store's tables stay on `Tag::Store` regions. 14: home table, collector, admission, import and the peer endpoint are cores on the injected clock; `fs.rs` becomes a thin driver of `blaze_core::Effect`s, and the pool has one loader used by daemon and simulation. 21: keys carry no home, checkout or maker-binary path (roots are rewritten; the maker is a codegen/schema version). 25: a batch's directory and a run are sorted, so one selection is one byte string and an export twice is identical. 43: DST below. 50: one disk measure, kernel-counted. 51: image, journal, placements, pins are records read through the pool; no mmap. 65: the index is per item and global; batch and extent are containers only.

## 5. Deleted, and what survives

**Deleted:** `blaze-gc`'s `Class`, `Keep::Refused`, TTLs, per-workspace caps, `.blaze-record`, `gc-ledger.json` as a file, `Collector::holds`; the store's use flags (`flags.rs`, `Read/ReadBefore/New/NewBefore`), the cold-tier settle as a second mover, `Standing::OverBudget` and `Warner` as the mechanism; `index.rs` (the SwissTable file), the delta table's role as an index (`INDEX_AFTER`), `rebuild.rs`; `RecordHeader` (96 bytes); `sealed.rs`, `Sets::{seal_at_once, seal, quiet, adopt, follows}`; pins as key lists (`pin_add/pin_change` sorting every key); `peers.rs` and `<machine>/std/<makers>`; `remote.rs`'s ask/answer wire, `blaze_global::bundle`, `blaze-pack`'s manifest, spans and `Import` re-put; `Loader::Pumped`; `Effect::Map` in the store; `FAILURES_MOST`; `blaze clean --unkept` as distinct from `blaze gc`.
**Survives:** content keys and `Kind`; per-worker segments and the one-barrier commit with a head flip; the pool and its DST; per-block CRCs; FastCDC chunking for large outputs; `place` by clone; pack retirement (`collect_take/copy/seal`) and its simulation; `sets.rs` listings (as `children`); the lease (now only on a checkout's placed directory and a home); trash with its marker and atomic rename; Ed25519 heads and the trust table; signed-request peers.

## 7. Unsound, unknown, or to measure first

1. **What is in `build/` (463.8 GB against a 4.5 GB store)?** If it is clones of store records, it is cheap and 4.1 is right; if it is bytes the store never held (incremental state, objects written in place), those must become records first. Answer: the lane diagnosing the home classifies `build/` by file kind and by `PRIVATESIZE` against apparent size.
2. **Does tracing cost too much at 10^7 records?** 320 MB of leaves read and 10^7 index probes a lap (arithmetic, not measured). Answer: the collector's simulation at 10^7 items with a span per lap; if over 10 s on a worker, memoize marked leaves by key (one bit a leaf, re-read only new leaves).
3. **Are `children` complete?** A record reachable only by recomputing its key (an item's inference record keyed by item + reads) must be named by its unit's listing, or it is collected live. Answer: DST oracle "after collect-everything, a rebuild of every live root makes 0 units", with the planted bug "listing omits derived records".
4. **Is an 8-byte key prefix in a run enough?** At 10^7 keys the chance of two sharing a prefix is about 3·10^-6; the directory compare makes it correct either way, but a collision costs one more page. Sound; measure nothing.
5. **Kernel-counted clone bytes.** Is `ATTR_CMNEXT_PRIVATESIZE` cheap enough to call for every placed file once a minute, and what is the Linux equal on XFS and btrfs? Answer: time it over a 10^5-file build directory; else account placed files as 0 while their key is in the store and full once it is not.
6. **Who wrote the 208 GB migration backup?** No code path was found; if an agent's script did, step 1's listing is the guard; if blaze did, name and delete that path.
7. **Does dropping the per-record content hash at rest weaken anything?** Today `get` checks it; the block CRCs catch rot, not a hostile local writer, but the store is already "the user's alone" (0o700). Answer: the owner decides; keeping it costs 32 bytes an item.
8. **Hard admission inside an edit.** A commit that waits for a collection lap could stall an edit by seconds. Answer: measure the lap at `Soft` on reth; the design intends `Hard` to be reached only when `Soft` could not keep up, and the span names it.

## 8. How to cut it (builders with 200K tokens, no compiler)

- **One mind (the store's owner):** the batch and run byte layouts, the head's new fields, `children` in the frame, and the cut of `lib.rs` (7,962 lines) into `commit.rs`, `open.rs`, `place.rs` before anyone else starts; then steps 3's deletion of `index.rs`/`RecordHeader`, which touches every reader.
- **Whole in a few files each, parallel after that:** (a) `home/table.rs` + `home/scan.rs` core and its DST (new crate, no dependency on the store's internals beyond `put/get`); (b) the disk-admission state machine and its simulation (`collect.rs`'s `Collector` only); (c) mark by ordinal bits over `Look::each_row` and `named_by` (`collect.rs`, `tests/collect.rs`); (d) index runs: builder, fuse filter, interpolation lookup, geometric merge (new `run.rs`, pure functions over byte slices, Hegel property tests against a `BTreeMap` model); (e) the batch codec (new `batch.rs`, same style); (f) import-as-layer and the head signature (`blaze-pack` shrunk to head + verify); (g) the thin `fs` driver replacing `blaze-gc/src/fs.rs` on `blaze_core::Effect`; (h) the checkout back-pointer and placement record in `blaze-cargo/src/serve/unit/layout.rs` and `cli/clean.rs`.
- **Must not be split:** the commit path's order of writes and syncs (4.5) and its storemodel run; the switch of the daemon from flags to tracing (step 2), since a half-switched collector forgets live records.
