# End state: `blaze check`, lints and diagnostics, and `blaze test`

Area: checking without building, `--fix`, `--replace`, the lint set and levels, diagnostics as data (made, kept, replayed, drawn, attributed), dependency warnings, test discovery, selection, running, doctests, flaky tests, benchmarks. Tree read: `/Volumes/Projects/blaze-int-1112` (paths under `crates/` unless they start with `docs/`). Status words: **measured** (a run, source named), **read** (from the code this session), **recalled** (another system's source or paper from memory, not opened), **design** (not run).

## 1. The job and the invariant

1. Say every error and warning of the code the user owns, in every configuration it is built in (lib, lib under test, bins, tests, examples, doctests; feature sets and platforms), without generating code.
2. After an edit, redo only the checks of the item edited and of what read what it changed; say everything else from records; on a no-op run nothing.
3. Make each finding data: which item, which rule, at what level and why, what it read, how to fix it; draw it for a person or hand it to an agent from the same value.
4. Know the tests of a program, run after an edit only those whose result can differ, each isolated, and keep each result as a record.
5. Apply fixes and renames by name resolution (`--fix`, `--replace A=B`), as edits to a view that is checked like any other edit.

**The invariant.** What a check says equals what a from-scratch check of the current sources, settings and lint levels says, as a set of findings; no finding at `deny` or above exists where the pinned nightly gives none, and none is missing under an `#[expect]` (rule 4: either refuses a program rustc accepts). A test reported without running has a record whose key and every recorded read hold now, and the report says it was not run and which classes of unrecorded input (clock, schedule, network) that run touched.

## 2. How the best systems do it

- **rustc** (recalled: `rustc_query_system/src/dep_graph/graph.rs` `emit_side_effects`, `rustc_middle/src/query/on_disk_cache.rs` `QuerySideEffects`; `rustc_lint/src/levels.rs` `shallow_lint_levels_on`, `lints_that_dont_need_to_run`; `rustc_lint/src/late.rs` `lint_mod`; `rustc_passes/src/dead.rs`; `rustc_resolve` `record_use`). A diagnostic is a side effect stored with the query node that emitted it and replayed when the node is green; lint levels are a per-owner query; lints allowed everywhere do not run; *a use is recorded by the resolver at the moment it resolves*. **Take** all four. **Not:** `effective_visibilities(())`, `live_symbols(())` and the resolver's unused-import pass are whole-crate (the resolver is not incremental at all); and pass order decides what is printed (an error in one body hides `dead_code` everywhere), which makes output a function of the crate, not of items.
- **Relax** (read: `compiler/src/check_reuse.rs` header; `harness.rs`, `harness_reach.rs`, `harness_live.rs`; `KNOWN_GAPS.md` §4). A verdict per crate: its rendered diagnostics, each with a sort place and gate flags `LATE` and `WF`, kept under the crate's text and re-validated by *dirty names* (a changed interface node dirties the names it is found under; a verdict stands while its crate's text writes no dirty name); an `Early` record under the load's certificate prints a whole check with no load. Tests run inside the program on libtest's semantics, a byte per executed slot, a live rendezvous so tests finish before the next edit applies. **Take:** gates as flags on stored findings (their gap 4 is what happens without them); the early record; the byte per slot. **Not:** crate grain (a body edit re-checks its crate); stored *text* (width, colour, paths and level are baked in); tests sharing one process's statics and heap.
- **cargo-nextest** (recalled: `nextest-runner/src/runner/`, `list/`, config `slow-timeout`, `retries`, `test-groups`, `leak-timeout`). A process per test is the isolation and kill boundary; the result vocabulary (pass, fail, flaky, timeout, leak, exec-fail); slow is reported, terminate is separate; a process group per test. **Not:** an exec, dynamic load and runtime start per test; listing by running every binary; no selection, no kept result; retries as the answer to flakiness.
- **Bazel and Buck2** (recalled: Bazel's test action cache, `--cache_test_results`, `--runs_per_test_detects_flakes`, tags `exclusive`/`external`, size timeouts; Buck2's `app/buck2_test` orchestrator over `ExternalRunnerTestInfo`, and buck2-change-detector's reverse-dependency selection; details of Buck2's caching of local test runs: not certain). A test result is an action result under a key of its inputs, replayed as `(cached)`; flakiness is found by running twice under one key. **Not:** target grain with declared inputs (any change under a test target reruns all of it). **Ekstazi** (Gligoric, Eloussi, Marinov, ISSTA 2015; recalled): dynamic dependencies per test with checksums are safe for deterministic tests, and collection overhead decides the grain. **rust-analyzer flycheck** (recalled: `crates/rust-analyzer/src/flycheck.rs`): shells out to `cargo check --message-format=json` and restarts it on save; take only the contract it shows, that tools depend on cargo's JSON messages, so that format stays as one view.

## 4. The end state (design)

**Where the one idea needs a statement of its own here.** (a) A lint over a whole crate (unused import, dead code, unreachable pub, an unfulfilled crate-level `#![expect]`) truly reads every item, so as one record it is per crate. It is split: the expensive half is a per-item row; the cheap half is a maintained fold over rows. (b) What rustc prints is a function of the crate (pass order, the abort before late lints, deduplication, "N warnings emitted"); those are projections at view time and are never stored. (c) A test's result is a function of its key and reads only if the test is deterministic; the record says which unrecorded inputs it touched, and the report says so.

**Records** (rule 51; store pages read in place; written once).
1. **Findings are a step value, not a store.** The per-function store of level 3 (lowering, inference, borrow check, MIR, keyed before lowering) gains the step `lint`; item heads (signature, attributes, impl header), a file's item pieces (syntax lints) and macro definitions get the same step in their own entries. Key = the subject's own key + the *lint universe* id (the set of lints at `warn` or above anywhere in the workspace's attributes and command lines; rustc's `lints_that_dont_need_to_run`, inverted). Reads = the step's `FactRef` reads; no second list. Value = `[Finding]`: lint id or error code; phase rank; gate flags (`LATE`, `WF`, `STASHED`, `FATAL`); the node the level is asked at, as a child path from the item's root; spans relative to the item, with the expansion chain by macro definition key; the message as a template id and **typed arguments** (a type or path is def keys and generic arguments, printed by the viewer with the viewer's names, which removes the reason `body_lints_clean` could keep only a bit); children; suggestions as item-relative edits with applicability; the facts read, narrowest first (`model.rs:341`, exists). No level, no file name, no line, no text.
2. **`levels(owner)`**: `hir-lint-levels` `lint_levels_on` as a record: key = the owner's lint attributes + its parent's levels id + the command-line set. A finding's level is a join at view time, so `-D warnings` or a `[lints]` edit runs no pass unless the universe grows.
3. **`uses(subject)`**: another value of the same steps: sorted rows `(target binding or def key, kind, the import bindings it was found through, the traits in scope it used, node)`. They are written by the one resolver and the one inference as they resolve (a `FactRef` name read already names the binding), so a use the compiler made is a use every lint sees; the second resolver in `used.rs` and its "count all as used" branch go, and the glob-import-in-pattern class cannot recur. `.clippy.toml` bans and `--replace A=B` are joins on these rows by def key (the reverse index fact → readers that codegen.md's manifest already keeps), never a walk.
4. **Folds** are maintainers (as incremental name resolution and impl tables are, docs/v2/plan/design/dbsp.md), one sans-IO machine each (rule 14), per crate scope and configuration: `import_used` (count of use rows through each import binding), `live` (reach from seeds over use rows: rustc's `dead.rs` seeds and marks, `names/dead/{seed,mark,report}` as its kernel), `effective_vis` (`effective.rs` `Build`: reads heads and re-exports, a body only through an `impl Trait` hidden type), `expectations`, `tests` (item attribute flags → the test rows of a target), and the merge over configurations (`reach.rs` `merge`, already plain data). Input: a keyed Merkle set `subject → row digest`. State: flat arrays as a sorted batch in the store, found after a restart by the input set's id; rebuilt from rows on a miss, which re-analyses no body. Output: rows `(subject, lint) → Finding`; only rows whose verdict changed are written. A body edit that leaves its use row equal moves no fold input. `live` is recomputed as a mark over integer arrays when a row changes (deletion in a cycle defeats counting); its bound is the crate's edges, to be measured.
5. **The check answer** is the request certificate's value for a `check` shape: per owned package, the Merkle set `subject → findings id`, the folds' output ids and counts. **The view** is one pure function `(answer, levels, ownership, gates, style) → output` in a crate with no compiler (`model.rs`, `emit.rs` and `emit/json.rs` import none today), run by the client: gates (hide `LATE` rows of a crate scope that has a required-analysis error; stop after `FATAL`), deduplication, rustc's order by `(phase, file order, node)`, closing lines, then drawing with the file's line index. A moved line or a changed width, colour or format reads the same records.
6. **Ownership is the request's, not the record's.** Owned = packages under the checkout's root, or named. For a package not owned only error-class findings of the items the owned code's records read are demanded; its lint step is never run, read, drawn, sent or counted (cargo's `--cap-lints allow`, extended to path dependencies outside the root). `blaze check -p dep` owns it for that request, and finds the same records another checkout made. This changes docs/terminal.md's "counted": a count would cost the passes.
7. **`result(test)`**: key = the test's root item key, its attributes, the executor (tier and policy, or the UB evaluator), target, host digest, sandbox policy. Reads, coarse first: the Merkle id of the rows its root reaches in the program manifest (static; unchanged means the result holds without looking further); then fine: each executed instance row (a byte per slot, set at entry) with its code key and the bodies built into it, the data rows those name (initial images of statics, vtables), and outside reads in outside.md's one form `(Ask, Answer)` hashed when read. Plus `nd`, the classes observed and not comparable: wall clock, monotonic clock, entropy not from the provider, more than one thread, a loopback socket, a child process, a signal. Value: outcome (passed, failed with code, signal or panic message, ignored, timed out, lost), output blob id, CPU and wall time, peak footprint. Lookup is a constructive trace; **two outcomes under one key and reads digest is a typed `nondeterministic` finding** naming the test and its `nd` classes (rule 21), which is what flaky means; nothing is overwritten and blaze retries nothing (rule 3). A manifest's `retries` is the user's request and reports FLAKY. Indexes in the store: instance key → results that read it; `Ask` → results.

**Selection.** After an edit the program delta (codegen.md) names the instance and data rows that changed; the index gives the tests that read them; those run, the rest are reported from records as kept, with what they were kept under. A new test, or one with no record, runs. A kept failure is run again by plain `blaze test` and replayed by `--kept` (for agents). `--all` runs everything and is how `nd` results are audited; a result that then differs is the finding above. **Soundness, said plainly.** Sound for a test whose behaviour is a function of the code it executes and the data it reads: files, listings, variables and child programs are reads; clock and entropy the provider answers from the key are not inputs. Not sound, and marked `nd`: wall-clock dependence, thread schedules, real time-outs. Refused in the sandbox and never kept outside it: the outside network. Each other's state: a test is a process with its own statics, a private write overlay and (Linux) a private loopback, so there is none to read; a package that needs libtest's shared process declares `shared` and gets one result for the binary. Positions: a `Location` or `line!()` is a data row read only by a run that raised a panic or called `Location::caller`.

**Running: a process per test, forked from a placed zygote; not a domain.** The launcher places the program once (code in a shared mapping, the statics image private), runs no user code, and forks per test; the child runs one root. One mechanism gives fresh statics, cwd, environment, descriptors and signal state, a kill boundary for a deadline, and a fault boundary. Domains (launcher.md §5, which codegen.md adopts) share a heap and an address space, so one test's wild write can decide another's kept result; they need a list of shimmed process-global calls, a second run "alone in a process" after `NeedsProcess`, and a rerun of every test that shared a crashed process: three smells and an unsound record. The measurement that would overturn this is in §7.3. The queue (`queue.rs`: critical first, one timer wheel, sans-IO) is the one runner for every command and screen; its replicas become forks of one zygote; admission is memory.md's gate (rule 50). Output goes to a per-test memory file read after exit (no reader thread, no `DRAIN`). A deadline is declared or absent (libtest kills nothing); "slow" is reported from the test's own recorded time, counted in CPU and sleep, not in time spent waiting for a core, so load fails no test. The harness is a synthetic root of the program made from the `tests` rows: in no crate's text and no item's key; a file output (`--no-run`, a debugger) gets libtest's `main` the same way.

**Tests are built as programs** (codegen.md): no test unit. `cfg(test)` is a scope of the front end; an item whose key is equal under both scopes has one record, so `build` then `test` shares every such row by construction. A doctest is a program with one root over a synthetic file keyed by its text (doctests.md's rules stay); `compile_fail` is a check whose answer must hold an error. Doctests of one crate share a zygote when their native link closure is equal. A benchmark is a program whose result is a measurement record keyed with the host digest; never kept as a pass, selected the same way.

**`--fix` and `--replace`.** Suggestions are in the findings; a fix is ops on a what-if view, checked as any edit (only edited items are re-checked), repeated to a fixpoint within 4 passes, committed when no new error appears (`cli/fix.rs`, as built). One fixer.

**What is shared with rustc, without running it** (rule 4). (1) The lint table (names, default levels by edition, groups, renames, future-incompatibility, `report_in_external_macro`): `blaze-lint-defs`, generated from the pinned commit's `declare_lint!`s at a toolchain bump, with its count-and-hash test. (2) Level semantics: `hir-lint-levels`, the only implementation. (3) The node a lint is attached to and the external-macro rule: one function from a node to its owner chain, used by every pass (the `#[allow]`-inside-a-macro-call class). (4) The facts a lint consumes are the compiler's own (use rows, the one inference, the one MIR), never a second derivation. (5) Gates and order, as the view. (6) Evidence: rustc's UI-test expectations at the pinned commit as fixtures (`emit/reference_tests.rs` exists), and a census on real projects whose own CI is warning-free: every blaze finding there at a default level is a false positive to fix (rule 7). A lint with no pass is listed by `blaze check` once, by name, and an `#[expect]` naming it is said to be unjudged; it is never silently fulfilled or unfulfilled.

**Bound for reth** (design; nothing here is measured). `blaze check` after one private body edit under 33 dependents: certificate miss naming the file, one file parsed, one item key moved, one body's steps run, its use row compared, zero or one mark, the answer's delta drawn. Target: **at most 50 ms client wall on the VM, daemon warm; 1 body linted (plus its closures), 0 bodies of any other item, 0 crates above visited, findings written ≤ 1 plus changed fold rows.** A signature edit adds the readers of that fact, from the fact index. A no-op `check` is the certificate hit (daemon.md's number) and reads 0 records of packages not owned.

**Memory.** Between requests: nothing on the global heap; fold state, findings, results and indexes are store pages. A pass's scratch is the task's frame, reset per item (rule 11). The client decodes the answer's findings into one frame, draws and exits.

**The rules.** 3: no retry, no "never kept" class, a lint with no pass is said. 14: each fold, the view, the check request (`Certified | Demand(subjects) → Folding → Answered`) and the test run (`Placing → Zygote → per test: Kept | Queued → Running(pid, deadline) → Recorded | Killed`) are sans-IO cores. 21: two results under one key is a finding. 25: the view orders by key; nothing depends on worker order. 43: each fold and the selector under Hegel simulation, oracle "findings and selected set after any edit sequence and crash equal a from-scratch run", planted bugs (a use row dropped; an executed row left out of a result). 65: no key names a crate; a fold's input id is a first check, not a key of findings.

## 7. Unsound, unknown, or to measure first

1. Is selection by executed rows sound on real suites? Mutate N single functions of reth and blaze; run all tests; a test whose outcome or output changed and was not selected is a missing read class (rule 23).
2. How many tests carry which `nd` class? Count from the sandbox's records on reth, tempo and blaze. If most async tests read the monotonic clock, "kept though `nd`" is the common case and the owner should decide the default.
3. Fork of a placed zygote against a domain start, Linux and macOS, on reth's largest test program. Over 0.2 ms a test, or macOS refusing fork after placement, reopens domains; under it they are not built for tests.
4. A private loopback per test: cost of a network namespace per fork (the measured 0.68–2.26 s was a whole sandbox per test), and macOS has none; what share of reth's tests bind a socket?
5. Size of use rows and time of one `live` mark on reth's largest crate; size of name-binding groups (end-state.md's question 3) bounds `import_used`.
6. How many of the 134 `lower/*.rs` lowerings format a type or path into the message? (A read of each.) They decide the size of step 2's port.
7. How many of the pinned nightly's builtin lints have a pass? A list from `blaze-lint-defs` against the passes' `GIVES` sets.
8. Does any real tool depend on rustc's order of diagnostics, as opposed to cargo's JSON fields? If so the view's order is part of the contract.
9. Findings inside proc-macro expansions: keyed by the expansion record; the external-macro rule needs the defining crate's ownership. Not designed past that.
10. Post-monomorphization errors under `check` (the owner's decision 2 in end-state.md): `check` demands no program, so it does not see them; say so or demand them.
11. Cost of a byte store at every function entry at tier 0 on a test-heavy suite: measure before step 5.

## 8. How to cut it

- **One mind:** the `Finding` schema with levels, gates and typed message arguments (step 1); the use-row vocabulary, which must be `FactRef`'s (with the engine's lane); the `result` key and read list (step 5). Each is one or two files and is compiled before anyone builds on it.
- **Whole in a few files each:** the view crate (`model.rs`, `emit.rs`, `emit/json.rs`, a new `view.rs`); each fold (its kernel file, its machine, its simulation test); the message-argument port, one `lower/*.rs` file at a time (mechanical, exact instructions, for Codex); `cli/test.rs` and `cli/live.rs` reduced to the queue's client; the `nd` classes in the sandbox's trace; the zygote in `blaze-launch-rt` (with the launcher's lane); the synthetic harness.
- **Not to be cut:** step 2 lands with the per-function store's lane, and step 5 with the program manifest's; neither is written against uncompiled code of the other.
