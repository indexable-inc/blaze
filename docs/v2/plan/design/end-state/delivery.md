# End state: proof and delivery (the evidence ladder, the one oracle, the gate, the measured table, the release train, the installer, how the work is run)

Tree read: `/Volumes/Projects/blaze-int-1112`. Read whole: `docs/v2/plan/design/end-state.md`; `end-state/daemon.md` 4.6-4.8 and 6-8, which this builds on and disagrees with by name in 4.9. Each fact is **measured** (with its source), **read** (code or a doc, this session), **observed** (the main agent's facts of 2026-11-12) or **design**. External systems are marked read or memory.

## 1. What this area must do, and the invariant

- State each thing blaze promises once, and hold it to evidence of a named strength (tested, simulated, model-checked, proved) produced on a named tree.
- Keep main a tree that passed: it builds, every test target compiles, its tests equal the expectations, its work counts equal the recorded ones.
- Find a wrong incremental answer before a user does and a slower edit loop before it is a day old.
- Ship only bytes that rebuilt blaze and passed its tests; install only bytes whose identity was checked.
- Let many short-lived writers (200K tokens each) change one tree without anyone building on code nobody ran.

**The invariant.** Nothing is believed without a verdict record: which check, on which tree, by which builder, on which machine class, with the non-empty list of things that ran and the outcome of each. Main's head, a release's channel, a ledger status, an invariant's level and a sentence told to the owner are functions of verdict records; never of a log someone read, a file that exists, or the absence of a failure.

**Fit to the one idea.** It fits without change: a verdict is a record `(key, reads, value)`. Key: the check's identity and the builder's. Reads: the test binary's content id (itself made of unit records), fixtures, variables, the seed, and for a time the machine's identity. Value: the ids that ran, each outcome, the counts. It is the answer until a read differs, so a gate costs the tests whose reads moved, and "did it run" is a type, not a convention. Where the idea needs care: the gate's verdicts are made by the thing under test (4.5 says how that circle is broken).

## 2. How the best systems do it

- **The merge queue: bors, Zuul, Uber's SubmitQueue** (memory: Hoare, "The Not Rocket Science Rule", 2014; Zuul's dependent pipeline; Ananthanarayanan et al., EuroSys 2019). **Take:** what is tested is the merge result and main moves only to the tree that was tested; a batch that fails is bisected and the culprit dropped; two changes whose reached targets do not meet need no joint test (blaze has that set: `scripts/src/bin/changed.rs`). **Not:** speculative builds of every order (machines blaze does not have), or fixing forward in the shared tree.
- **rustc-perf** (read: `site/src/comparison.rs`, `significance_threshold` = Q3 + 3 x IQR of that test case's own historical percent changes; `DEFAULT_SIGNIFICANCE_THRESHOLD` 0.002; instruction counts first). **Take:** deterministic counters gate; a threshold per row from the row's own history. **Not:** measuring after the merge with a weekly human triage, where a regression is noticed by a person or not at all.
- **TigerBeetle's CFO, with Build Systems a la Carte** (read: tigerbeetle `src/scripts/cfo.zig`, branch `release`: machines loop on fetch-main and random fuzzers and push `(commit, fuzzer, seed, outcome)` rows, failing seeds kept first; memory: Mokhov, Mitchell, Peyton Jones, ICFP 2018; rustc's `-Z incremental-verify-ich`). **Take:** correct means every kept value equals a recomputation from the current inputs; that one statement is run all the time on idle cores, its output is a table of seeds per commit, and trust is that table; in production a sample of hits is recomputed and compared. **Not:** a fuzzer per component each with its own notion of right.
- **CompCert, CakeML, Alive2; TUF** (memory; the first three are cited in `formal-verification.md` 456-474; Samuel et al., CCS 2010). **Take:** a chain of refinements with the trusted remainder listed; a small checker per run where a proof is too large; a channel pointer that is signed, numbered and expiring, so a client refuses an older or stale one. **Not:** proving the front end first; TUF's whole role hierarchy.

## 4. The end state

### 4.1 The verdict (one record form for every check)

`Verdict { check, tree, builder, machine, ran: NonEmpty<(Id, Outcome)>, counts, requests }`, a blaze-format record (rule 51) in the store of the machine that ran it, travelling as a pack. `ran` cannot be empty by type: "0 tests ran, ok" is not constructible, which is `ran.py`'s rule moved into the type. `builder` is cargo's or a blaze's identity, so a number made with cargo standing in can never be read as blaze's (rule 2). A run that died before producing a verdict is `NoVerdict(cause)` and may be run again; a second verdict under the same key that differs is `Unstable(id)`, a typed refusal (rule 21), never a retry (rule 3). A test's verdict is reused only when its reads were traced (a simulation test reads nothing outside; a real-process test runs in the sandbox); otherwise it runs every time.

### 4.2 Claims (one table, one ratchet)

`Claim { id, statement, check, expects, level, scope }` with `expects` one of `Pass`, `Fail{cause, issue}`, `Unstable{owner}`, `Count{name -> exact}`, `Paired{row, threshold}`. Sources: the doc comments `invariants.rs` already scans (the code stays their one home), and one file per row under `claims/` (as `agents/` is laid out, so rows never conflict). `judge(claims, verdicts) -> Green | Red(claim, was, now)` is one pure function in a small crate, `blaze-claims`, with property tests. One ratchet replaces the eight of 3.3: on main the set of `Fail` and `Unstable` rows and every `Count` may only shrink; a new `Fail` row is accepted only in the change that adds its test (a reproduction) or with the owner's signature; a listed test that passes is red until its row is deleted. A status is never written into the tree: a ledger row's state and an invariant's level are the join of claims with the verdicts of main's head, computed when asked. A level is earned by a run: `simulated` needs a verdict from the simulation driver with the seed count, and every control's verdict must show the planted bug caught on the same tree.

### 4.3 The gate: four checks, one way in

Main's ref is moved only by the queue, to the exact tree a batch was judged on; no admin merge, for people or agents. The queue is a sans-IO machine (`Queued -> Batched(tree) -> Judged -> Landed | Dropped(pr, claim)`) with its own simulation (rule 43): batch what is queued, judge, on red halve and judge again, drop the culprit to its lane with the claim that moved. GitHub's merge queue on the ix runners is its first driver (`merge_group` is wired). The minimal set, all on the merge candidate:

- **G1 compiles.** `check --workspace --all-targets` by cargo with the pinned nightly and by the stage-0 blaze. Main always builds and every test target compiles, or nothing lands.
- **G2 tests equal expectations.** Every test binary whose reads moved runs to its end under a deadline per binary (ten times its recorded duration, floor 60 s); a hang is that binary's `Fail`, naming it. `judge` must be green.
- **G3 counts are exact.** With the tree's own blaze, on hello-world, the bstd hello-world and `harness/v2/smoke` (build scripts, a proc macro, C): for no-op, no-op after restart, comment edit, body edit, signature edit and first edit after restart, the jobs, admissions, units remade, rows run, rows verified, functions lowered, files hashed and bytes written equal the `Count` rows in the tree. A change that moves a count changes the number in its own diff, in either direction, so it cannot land unnoticed. The revision suite is judged by its counts; `max_ms` goes. Counts do not depend on load.
- **G4 the oracle's budget** (4.5) for the crates the change reaches.

Times are in no gate. That is `daemon.md` 4.7's L3 rule, and I keep it.

### 4.4 The measured table (how a slower edit loop cannot land unnoticed)

- **Projects and rows.** reth, tempo (once it builds cold) and **blaze itself** (the project edited hundreds of times a day here): no-op; no-op after restart; end-of-line comment; private body edit in a leaf; body edit under N dependents (reth: 33); signature edit; first edit after restart; warm and peak footprint (rule 50). Cold builds are shown, not judged (rule 60). Relax is a third arm on hello-world, as `rival.yaml` already takes turns. Each row has counts (exact against the tree's rows), user-mode instructions of daemon and client, wall time and footprint.
- **Where.** One machine that does nothing else (4.9, the ask). Not the build VM with a cpuset.
- **Compared how.** Never against a stored time. The head's binary and the last measured head's binary run interleaved in one session (ABAB, 10 pairs after 2 warm-ups), both built by one builder from named trees; the number is the median paired ratio. `crates/blaze-bench`'s paired runner already does this for microbenchmarks (`bench.yaml:1-6`).
- **Noise bound.** Counts: zero. Instructions: the larger of 0.2% and Q3 + 3 x IQR of the row's own past deltas. Wall and footprint: the larger of 2% and the same formula. A row regresses when it is over its bound in two sessions in a row. Each table carries its own controls: an A/A pair (the same binary in both arms) must come out inside the bound, and a planted 5% delay in the body-edit path must come out flagged; a table whose controls fail is `INVALID` and holds no number.
- **What follows.** The machine always measures the newest head against the last measured one, so each table covers a contiguous range. A regression bisects that range with paired runs, and the queue takes no change reaching the edit path until the culprit is reverted or the row is re-recorded by a commit that says so. When the unmeasured range passes K commits the queue stops: a missing table is a red gate, not a quiet one.

### 4.5 The one soundness oracle

**Statement O.** In any state reached by any history, every record that holds equals a recomputation from the current inputs. "The request's answer equals a fresh home's" (daemon.md I1) is O for the certificate; "a store hit is the bytes a compile gives" is O for a template. Because end-state.md's review makes the record one primitive, O is checked at one place.

- **One generator, one model, three drivers.** A sans-IO crate `blaze-oracle`: `Model` (what the program must print, refuse, test), `History` drawn by Hegel (`vendor/hegeltest`, `stateful.rs`), `judge`. The alphabet is the union of today's six: `Edit` (every kind of `fixture.py`'s slots and `generate.rs`'s), `Save` (write, rename, truncate, twice, mid-build), `Request`, `Stop`, `Kill` (a crash at any sync point, unsynced writes torn), `Cancel`, `Restart`, `Evict` (pool pages, a collection, memory given back), `Import` and `Export` (a pack from a home built at another path), `Beside` (a second checkout), `Moved` (the checkout renamed), `Bumped` (a newer blaze over this home, an older blaze over a newer home), `Racing` (two requests), a stat stamp taken too close to the change. Drivers: in process over the real store and VFS under `blaze_core::sim` (thousands of histories a minute); real processes for what only a kernel shows, counts only; and real projects, where an edit is a seeded mutation of a real function and "clean" is the project's own test verdicts and output bytes.
- **In every real run:** a sample of record hits is recomputed and compared, at a fixed CPU budget under 1%, on in CI, in the agents' daemons and during promotion; a difference stops the build with the record and the read that was missing, and serves neither value (rule 3). This generalises `verify_store`.
- **Read completeness, checked directly:** for a sampled record, change an input that is not in its reads and recompute; a different value is a missing read, found without waiting for a wrong program.
- **How often, derived, not chosen.** Each planted bug has a measured number of histories until caught. A change's G4 budget is 4.6 times the slowest plant's mean among the crates it reaches (a 99% chance of catching a bug of that size); a plant not caught in the budget is a blind oracle and red. Between gates the simulation driver runs all the time on idle cores, as CFO does, writing `(commit, generator version, seed, outcome)` verdicts; a failing seed opens a claim with its replay line. A release needs 100 times the gate budget on its exact commit with no failure, and a real-project history on reth. The trust number shown is histories since the last failure, by event kind.
- **The circle** (a gate that reuses verdicts is trusting blaze's own incrementality): verdicts are reused only from the stage-0 release, never from the tree's blaze; the sample above re-runs kept verdicts clean; promotion runs everything cold.

### 4.6 Where proof pays first, and what is honest about Lean

Ranked by what rests on the code, how small and pure it is, and how badly tests cover its failures:

1. **The record primitive: prove it in Lean.** `holds` and lookup refine a reference model (a map from key and current digests to a value). It is small, safe and pure, all three levels stand on it, and its known defect (a base whose slots are full is never stored again) is the kind a proof finds. This would be the first of 165 invariants at `proved`. Caution: `formal-verification.md:452` says hir-ty-lean's Rust tests have not run and one function (`fnv1a_from`) has gone through the translator.
2. **The store's commit protocol and the request machine: model-check, not prove.** As sans-IO machines over `sim/journal.rs`, enumerate every crash point and every subset of unsynced writes up to a bound, instead of sampling them (memory: ALICE, Pillai et al., OSDI 2014). A Perennial-style proof is v3 of the plan and years away.
3. **MIR passes: translation validation with a coverage number.** The gate runs each pass's checker on reth's and the compiletest corpus's bodies and reports validated, refused and outside-the-subset. That fraction is the honest measure of rule 57, with the length of the trusted list.

**The distance.** `lean/` is 18,670 lines and about 944 theorems (read, by `rg`), with no `sorry` and the three standard axioms held by `lean_gate.py`. The semantics is a first subset: scalars, no aliasing (`formal-verification.md:502`); the passes proved are Lean specifications, tied to the Rust passes by `rfl` per function where the two agree (`RemoveStorageMarkers` does; `SimplifyConstCondition` does not, `:895-901`). Trusted: the front end up to MIR, runtime lowering, most passes, LIR, the stencils, LLVM, the linker and live patching (`:922-935`, `:959`). No compiler for a language of Rust's size has a verified front end. So the goal is restated as one that can be checked each day: the trusted list is in the tree with sizes and only shrinks, and the validated fraction only grows. Wrong code is found first elsewhere: every real project's tests under both producers (dev stencils, release LLVM) with the verdicts compared, which needs no rustc (rule 7), and the compiletest corpus as `Count` claims per suite.

### 4.7 blaze builds blaze: reached and kept

Reached by making blaze a row of 4.4: the rule's own measure (a warm rebuild after a one-function change under a minute, cold inside 64 GiB) is then on the table every day beside reth's. Kept by a daily job that makes verdicts: stage 1 (the last stable builds the tree) builds stage 2, stage 2 builds stage 3, and **stage 2 equals stage 3 byte for byte** (rule 25); a stage 1 from cargo must give the same stage 2 (two unrelated compilers agreeing, memory: Wheeler's diverse double-compiling); stage 2 runs the whole test table and `judge` is green with `builder = blaze` (`known-failures.toml` already has rows "fails when blaze builds and tests it, not under rustc": they become `Fail` rows scoped to that builder, and only shrink). `.github/blaze-version` is moved by the promotion itself, through the queue, so stage 0 is never older than the last stable. When the row is under a minute, G1 and G2 change builder to blaze on a warm daemon (`design/ci.md`) and a gate costs the diff.

### 4.8 Release, install, update

- **A canary** is cut only from a tree the queue landed. **Promotion** judges the published bytes: (1) they rebuild blaze at their own commit to a fixpoint (4.7); (2) the stage 2 test table is green; (3) the oracle's release budget is met on that commit; (4) the measured table has no regressed row against the current stable, paired; (5) `Bumped` histories pass in both directions: a home the current stable wrote is taken over soundly, and the stable finds its own home intact after the candidate ran. Then the release is signed and the channel pointer moved.
- **The pointer** is `{channel, version, digest per host, number, expires}`, signed by the key the owner picks (end-state.md, the owner's decision 3). A client keeps the highest number it has seen per channel and refuses a lower one or an expired one; a yank is a signed pointer naming the replacement.
- **Install is a state machine with a simulation**: `Fetched -> Verified(signature, digest) -> Unpacked(versions/<v>/) -> Identified -> Current`. `Identified` runs the binary's own `--version` and requires the release id and tree id in the signed manifest. `Current` is one rename of a link; the previous versions stay, so going back is a rename. A crash at any point leaves the old `current`.
- **A local build can never sit in a channel's place.** It is linked by name (`blaze toolchain link <name> <path>`, as rustup does) under `dev/`, and says `dev:<tree id>` in every version line; the launcher refuses a binary under `versions/` whose digest is not the manifest's. The observed bisect install is then impossible by layout.
- **Updates** are looked for off the request path, at most daily; a workspace pinned with a digest never floats.

### 4.9 How the work is run (with one VM), and where I differ from `daemon.md` 4.8

I keep its five points in substance: a design gate, interfaces by one mind and compiled, builders compile their own crate, a worktree per lane, a queue that advances only on what passed. Differences and additions:

1. **There is no integration tree. Main is it.** The unit of landing is one claim: the smallest change that moves one row or deletes one thing, compiles alone and passes G1-G4. `daemon.md`'s L0-L3 on "every snapshot" become the queue's check on the merge candidate, on the CI runners, which already fork a warm snapshot. A redesign lands as compiled types first, then pieces each behind its own simulation test, then one change by the coordinator that wires it and deletes what it replaces. int-1112 is carved into such changes in dependency order after main's gate is green; what end-state.md lists as superseded is dropped, not carved.
2. **Reserved cores are not a quiet machine.** A cpuset does not reserve memory bandwidth, the page cache, the disk or a balloon (3.6: 39.5 s to 190 s). **The ask of the owner: one measurement machine**, an ix VM pinned to a host CPU class with committed memory (`contributing.md:338-340` already prescribes it) or bare metal, 64 cores and 256 GiB, running one job at a time: the tables, then real-project builds and real-project oracle histories. That also takes the hour-long tempo build off the build VM. Rule 34 then names two machines by job: `blaze-vm` builds, the other measures. And not twice a day: as often as the machine turns, with the stop rule of 4.4, so a bisect is bounded by K.
3. **Who compiles:** the author, `check -p <crate> --all-targets` and that crate's tests, in a worktree whose build directory is cloned from main's warm one, through one jobserver for the whole VM so the load is bounded by tokens and not by manners. Lanes run no workspace build, no real project, no measurement. A crate whose warm check passes 60 s or a file over 1,500 lines is a `Count` claim that only shrinks (`serve/job.rs` is 9,000 lines): what a builder cannot read, a builder cannot change.
4. **Who measures:** only the measurement machine. A lane asks for a table by tree id and gets rows with their controls; a lane never reports a time.
5. **A design is reviewed before code**, as `daemon.md` says, plus two things. It states the number it predicts and the cheapest run that would refute the design. And a mechanical alarm for rule 66's class: three landed changes citing one target whose number has not moved inside its bound flips the row to `redesign`, and the queue takes no further fix against it until a reviewed design exists.
6. **Task size from the context limit.** A brief is generated from the claim (`ledger brief <id>`): the row, the compiled signatures it fills, the test that must pass, at most three files to write and 1,500 lines to read by anchor, and only the how-to rows whose paths match. Annoyance rows get a typed state (`open | fixed(commit, claim) | accepted(why)`): fixed must name the claim that would now catch it (rule 54).
7. **What is told to the owner is generated** from claims and verdicts; a sentence with no verdict id is printed as a guess (rule 61). **Scratch has a lease:** a lane's worktree, build directory and homes live under one root with an expiry the runner enforces (observed: 192 GB of forgotten homes); the store's own bound is `disk.md`'s.

**Rules met.** 3: one way into main, no rerun of a verdict. 14, 43: the queue, the installer, `judge` and the oracle's model are sans-IO machines with simulations. 21: a verdict's key holds builder, machine and seed; two values under one key is `Unstable`. 25: counts exact; stage 2 equals stage 3. 46, 53: status and level are computed from verdicts. 50: footprint rows. 51: verdicts and tables are records. 65: a verdict per test and per row, never per crate or per run.

## 7. Unsound, unknown, or to be measured first

1. Why were 296 of 300 gate runs red? Classify them by failing job and cause from the run history. If most are timing or the runner, step 3 fixes them; if most are real, step 1 is larger than it looks.
2. How long is a quiet full test table, on the VM and on a CI runner? Not known: no clean table exists (observed). It sets the batch size.
3. Are the work counts identical run to run on one tree? Build each small project twice from clean and diff the `requests` rows. A count that varies is not a gate until its cause is named.
4. Which machine is quiet enough? Run the A/A table on a pinned ix class and on bare metal; take the one whose bounds are tighter. Does `redit-10`'s drift happen with committed memory?
5. Does cargo take one inherited jobserver across lanes, and does it bound the VM's load? Two lanes, one token pool, read the load.
6. Are blaze's real-process tests' reads traced well enough to reuse a verdict? Count the tests that run sandboxed with a whole trace. Until then only simulation tests are reused. And is the hit sample affordable at 1%? Measure a reth body edit with it on and off.
7. How many histories does each existing plant take to be caught? If one needs more than 100,000, the generator is drawing the wrong things.
8. Is stage 2 equal to stage 3 today? Never run (not measured); it is the first real test of rule 25 on blaze itself.
9. Can hir-ty-lean translate the record primitive? Its tests have not run. Try that function before promising the proof.
10. What fraction of pass applications on reth lies inside the Lean subset? If it is under a tenth, the work is the semantics (aliasing), not more pass proofs.
11. Does GitHub's queue bisect a failed batch the way the machine needs on the ix runners, or does the queue need its own driver? Read its settings and try a planted bad change among four.
12. The owner's: no way around the gate, admin merges included; the second machine; rule 35 narrowed to "lanes run no workspace build and no measurement"; the signing key.
