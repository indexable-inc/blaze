# End state: from checked code to a running program

Area: units, monomorphization, code generation, placing/linking, the launcher, live patching. Tree read: `/Volumes/Projects/blaze-int-1112` (paths below are under `crates/` unless they start with `docs/`). Status words: **measured** (a run, source named), **read** (from the code this session), **recalled** (from memory of another system's source or paper, not opened this session), **design** (not run).

## 1. The job and the invariant

1. Turn each checked function instance the program can run into machine code, once per machine, whatever crate, project or daemon asks.
2. Say which instances a program is (its roots' closure) without redoing that on an edit.
3. Put the code where it runs: in a running process (goal `edit`) or in a file (goal `max`, `build`), by one placer.
4. After an edit, redo only instances whose own code or recorded reads changed, and change only their slots in the running program.
5. Carry positions (panic locations, line tables, debug info) so a moved line recompiles nothing.

**The invariant.** At every commit point the placed program equals, by Rust's semantics, the program a from-scratch build of the current sources gives: every slot names code from a record whose key and every read hold now; no caller can enter a body of an older revision after the transaction commits; and the manifest and any written file are a function of the sources and settings alone (no schedule, address, path or clock).

## 2. How the best systems do it

- **Relax** (read: `compiler/src/cache.rs` header, `cache/deps.rs`, `cache/image.rs`, `reload.rs`, `jit.rs`). One code entry per function slot, keyed by content, and "an entry also names the slots whose RIR its code took in (inlined bodies, nounwind answers) with their keys: it links only while those keys are unchanged". Functions compile on first call behind a per-function patch table; a startup image (`image.rs`, `prelink`) stores the placed code of the slots a start needed, relocations against identity tables, and installs it in one pass. An edit is one all-or-nothing transaction (`reload.rs` steps 1 to 6). **Take:** the function as the only unit; reads recorded on the code entry; lazy first call; the prelinked image; the transaction. **Not:** the program inside the compiler's process (blaze's launcher keeps it in its own); "per-crate code stores named by the interface fingerprint" and the whole-sysroot `atomic` fingerprint in every key (per-crate keys, rule 65); "its own body and position" in the code key (a comment edit recompiles: 90 ms measured).
- **Zig** (recalled: `src/InternPool.zig` dependency tracking per analysis unit with dependees `src_hash`, `nav_val`, `nav_ty`, `interned`, namespace names; `src/Zcu/PerThread.zig` `linkerUpdateFunc`; `src/link/Elf/ZigObject.zig`). Each function instance is analysed and code-generated alone, on a queue separate from semantic analysis; the linker gives each its own atom with growth padding and routes calls through an offset table so an update rewrites one atom and one entry. **Take:** codegen per instance fed straight from analysis with no partition step; the indirection that makes a patch one word. **Not:** padding inside a file (blaze's patch room measured its disk cost and is the thing to delete); one compilation's state as one blob with no cross-project sharing.
- **rustc** (recalled: `rustc_monomorphize/src/collector.rs`, `partitioning.rs`, `-Zshare-generics` and the `upstream_monomorphizations` query, `rustc_codegen_ssa` work products). The collector walks from a crate's roots; instances are partitioned into CGUs (two a module); incremental reuse is per CGU; a generic instance is shared only when an upstream crate happened to instantiate it. **Take:** the collector's rules (blaze's `recursion.rs` already ports the limit) and `cross_crate_inlinable` as a fact. **Not:** the CGU (an edit recompiles a module's worth and relinks all), and an instance owned by a crate.
- **Build Systems à la Carte** (Mokhov, Mitchell, Peyton Jones, ICFP 2018; recalled). A record found by key and then verified by its reads is a *constructive trace*: several values may sit under one key, chosen by the digest of the reads. That is the lookup form needed for optimized code, whose reads are known only after compiling. Fast baseline code: copy-and-patch (Xu, Kjolstad, OOPSLA 2021; recalled), which `blaze-stencil` is.

## 4. The end state (design)

**The answer to the hard question: yes, the crate-sized unit is the root problem, and codegen has no units.** A cargo unit survives only as the front end's scope (a crate with its cfg and features) and as a thing that names roots. Nothing is compiled "for a crate"; code is demanded by a program's roots and by nothing else. There are four records, all in the store, all in the form of end-state.md (`key`, `reads`, `value`).

1. **Instance record** (`inst`), one per function instance per MIR mode. *Key*, computable before any lowering: the item's own code identity (level 3's per-function key; positions excluded), the content id of its type arguments (`Instance::args`, already by content), and the settings that change its MIR or LIR (goal/tier, panic, overflow checks, debug assertions, target). No requester, no crate, no image. *Reads*: every fact taken while monomorphizing and lowering, in the one vocabulary `FactRef` (`parts.rs`): the impl each trait call selected (negatives included), layouts of types used by value, callee signatures and ABIs, constants evaluated; at the optimized tier also each body built in (by code identity), each fact spent (`body.inlined.relied`), each devirtualization. *Value*: the references in MIR order, each by its own key recipe (item, args) or as a static, extern symbol, vtable or `Loc(span ref)`; the LIR shape key; what the recursion limit counts; or the instance's error (an error is a value, with the item it names). Lookup is a constructive trace: `key -> [(reads digest, value)]`; a row is taken when its reads hold, checked coarse first (the crate seal of each read), fine only under a seal that moved. Tier 0 and optimized code are the same mechanism with shorter or longer read lists; the two folded template keys go.
2. **Code record** (`code`): key = LIR shape key (canonical LIR bytes with references by place) + backend settings + toolchain; no reads, since LIR is its whole input; value = the template (`template.rs`: code, relocations by place, unwind, line rows relative to the item's first line). This is today's memo made a store record; `Vec<A>::drop` and `Vec<B>::drop` stay one compile. LIR is not stored (lir.md's decision stands): on an `inst` and `code` hit no MIR or LIR exists at all.
3. **Facts record** per strongly connected group of functions, keyed by the group's Merkle code identity (`code-identity.md`): the effect sets `facts_of` answers. Made by a keyed worklist bottom-up over callee records, never a depth-first query. Only an optimized `inst` reads it; a tier 0 build asks for none, and std's bodies under goal `edit` are tier 0 like everything else (the exception in tiers.md is deleted, not kept).
4. **Program record** (`prog`): key = roots (item keys of `main`, of each test, of a cdylib's exports), policy id, target. *Reads* = the `inst` rows it reached, held as a keyed Merkle set (`driver/delta.rs` `BuiltId` is this already). *Value* = the manifest: rows `(instance key -> inst row, code key, slot)` sorted by key, static rows, the location table, natives, and two inverted indexes: item -> its instance rows, and fact -> the rows that read it. It is the certificate-like list the launcher places. A sealed sub-closure (every instance under `std::rt::lang_start::<()>`) is itself a record keyed by its root's instance key, so a new project reads std's closure as one record, not 14,000.

**Where a dependency generic's instance lives.** Nowhere in particular: under its `inst` and `code` keys, which name no crate. `HashMap<K, V>::insert` asked by twelve crates, two projects and two daemons is one key. Compiled once: in a daemon by the single flight on the key (`flight.rs`); across daemons by put-if-absent of deterministic bytes (two writers write the same record; a claim record with a deadline is question 7.6). The toolchain installs with a pack of std's common `inst`/`code` records and closures.

**What replaces the top-crate walk: demand, as one sans-IO state machine `Program`.** States: `Empty -> Demanding(frontier) -> Runnable(entry placed) -> Closed(manifest whole) -> Edited(delta) -> ...`. Inputs: "these item identities changed", "these facts moved" (from the front end), "record found/missed", "compiled". Outputs: lookups to make, describes and compiles to run, a `PlacementDelta` (slots to fill, data words to write, rows retired), errors.
- *Cold.* A worklist on every worker (`worklist.rs`, `frontier.rs` survive): visit = look up `inst`; on a miss the front end describes that one instance in the visiting task's frame, which is reset per item; then look up `code`; on a miss compile. Describe and compile interleave; there is no phase boundary and no crate in the path, so no last-unit tail. The program becomes `Runnable` when the entry and what the start sections name are placed; the rest fills behind it, and a first call to an unfilled slot raises that instance's priority (launcher.md's `Need`). `Closed` runs the whole-program checks (recursion limit by `recursion::check`, a symbol defined twice, instance errors) and reports them as diagnostics; a file output waits for `Closed`.
- *An edit. No walk.* The item index gives the edited function's rows; each is looked up under its new key (a miss describes and compiles it); its new references are diffed against the old row; only keys absent from the manifest are demanded (the frontier form, `near.rs`, becomes the only form). The fact index gives readers of a moved fact (a changed signature, layout or impl); those rows are re-verified, not walked to. The delta moves the Merkle set by its changed paths. Rows no root reaches are retired by a bounded mark over the manifest's flat arrays (`reach.rs`) at `Closed`, never on the edit's path.

**Placing.** One sans-IO placer core takes a `PlacementDelta` and yields writes; two thin drivers. (a) The launcher (`blaze-launch*`): one slot word a function, code appended, epochs retire old bodies, an edit is one gated transaction (launcher.md sections 1 to 4, as built). A placed image keyed by the manifest's Merkle id (Relax's `prelink`) makes a no-op start one mapping plus the slot table. (b) The file writer for `build` and `max` (`blaze-link`'s ELF, Mach-O and PE writers): direct calls, ICF (`dedupe.rs`), exact reach, no patch room. Under `edit` no linked file exists.

**Positions.** No position is in an `inst` or `code` key. A panic `Location` is a data row the code names by place; its line and column come from the location table, a record that reads one file's line index. A moved line rewrites those rows' words in place inside the transaction and compiles nothing. Line tables are stored relative to the item; absolute lines are the item's start (one position fact) plus the row. DWARF is written only by the file driver; the launcher answers a backtrace or debugger from the manifest.

**Closures.** A closure's identity is its owner's item key plus the content hash of its own expression, with an ordinal only among equal siblings; inserting a closure renames no other.

**Tests are programs.** A test binary is a `prog` whose roots are the tests; a test's result is a record keyed by the Merkle id of the rows its root reaches plus its traced reads (`reach.rs` `Built::reached`), run as a domain in one launched process (launcher.md section 5).

**Memory.** Held between requests: nothing on the global heap but the single-flight table of keys in flight. Manifest rows, templates and indexes are store pages read in place through the pool (rule 51). A describe's MIR and a compile's LIR and LLVM context live in the visiting task's frame and are reset per item (rule 11); peak is workers times the largest function, not the program.

**The rules.** 3: a missing record is a miss that runs the work; a record that is there and does not read, a backend needing a reference the list lacks, or a patch that cannot apply is an error naming the instance; no retry and no "walk whole otherwise". 14: `Program` and the placer are sans-IO cores; drivers do the store, socket and file IO. 21: two values under one `(key, reads digest)` is a typed refusal naming both (as `records::sorted` does now). 25: manifest order is key order; slot numbers are process-local and in no output. 43: `Program` under Hegel simulation, with the oracle "manifest and placed bytes after any edit sequence, crash and reordering equal those of a cold build of the final sources", and planted bugs (a read left out of an `inst`; a retired row left in a slot). 50: admission of a visit is by the footprint of its frame. 65: no key names a crate; a crate seal is only the first check.

## 7. Unsound, unknown, or to measure first

1. Is an `inst` key computable before lowering for a function in a crate being edited? It depends on level 3's per-function store. Answer: read that section's key; if absent, step 2 cannot precede it.
2. How many reads does one describe record, and does verifying them cost less than describing? `parts.rs` caps a unit at 2^20 parts. Answer: count `FactRef`s per describe on reth before step 2.
3. Are recorded trait-selection reads complete (a new impl, specialization, a negative read)? Answer: the edit fuzzer of `code-identity.md` with the oracle of rule 43; a code review is not evidence.
4. Under `edit` a post-monomorphization error arrives after the program started. Rule 4 is kept (every accepted program runs), and `build` refuses before writing; is a late refusal acceptable to the owner? Ask.
5. Can the recursion limit and "symbol defined twice" be checked on a delta? Guess: yes for new rows only; unproven. Answer: a property test against `recursion::check` over the whole graph.
6. Two daemons compiling one key at once: wasted work, not wrong. Is a store claim with a deadline worth it? Answer: count duplicate puts on a shared store.
7. What every-call-through-a-slot costs at run time: not measured at reth's scale. Answer: reth's test suite time, launched against linked.
8. Does tempo fit the launcher's 2 GiB area (631,397 functions)? Answer: sum template sizes from the store.
9. Store load: over a million small records a program and tier. Answer: put rate and lookup time on tempo; packs per sealed crate set if needed (git packfiles).
10. Why hello-world is 33–36 MB, and what reth's 600 s is made of: not known; step 0.
11. Zig and rustc are cited from memory; a builder who leans on a detail must open the file named.
