# Toolchain and language surface: the nightly, std, bstd, editions, targets, C inputs

Lane toolchain, 2026-11-12, read on `/Volumes/Projects/blaze-int-1112`. Every claim is **measured** (with its source), **read** (code or a doc, not run), **memory** (another system, cited from knowledge, not re-read today) or **design**. Nothing was built or run.

## 1. What this area must do, and the invariant

- Give every build the same language, standard library, C compiler, headers and linker inputs on every machine, chosen by the blaze a workspace pins and by nothing installed on the machine.
- Make a new project's first build compile nothing of std, bstd or common dependencies: their records are found by key, fetched and checked.
- Make a daily nightly bump and a daily blaze release cost what changed, in download and in work.
- Keep blaze's language changes (editions, extensions, bstd) opt-in in one front end, so a program that does not opt in has the same keys and bytes.
- Cross-compile from a clean environment to the targets kept, C included.

**The invariant.** (a) *Closed inputs*: every byte that can change an output is in the workspace, or in a tree named by a BLAKE3 the blaze binary or the workspace's lock holds, or is a traced read of a declared machine input (the macOS SDK, a `system` tool) recorded with its digest; a `PATH`, `CC`, `LIBCLANG_PATH`, rustup directory or installed header is never read. (b) *Portable keys*: no key holds a home, checkout or tool directory path, a host's CPU probe, a profile's name or the making binary's whole identity; equal inputs on two machines are equal keys. (c) *Opt-in*: with no blaze bit on, no query result depends on a blaze extension's code.

## 2. How the best systems do it

- **Relax** (read: `front/src/lazy.rs` `DemandImage`, `FileIndex`; `compiler/src/lib.rs:458` `sysroot` = "Relax's std sources"). Take: std is never *built*; it is *reached*. Only files the program's names reach are parsed, which is why its hello-world is 0.69 s cold (measured, brief) against blaze's 72.6 s and 257 units (measured, brief). Do not take: nothing is shared across machines, and std is found by a path option.
- **Zig** (memory: `src/glibc.zig`, `lib/libc/glibc/abilists`, `src/libs/musl.zig`, lazy declaration analysis in `Sema`/`Zcu`). Take two ideas: the C library is *data* (one abilist for every glibc release, headers for every target, crt from a few lines) so one download cross-compiles everywhere, and std is analysed per declaration on demand. blaze-link already took the first (`target/shipped/glibc-<arch>.abilist`, `shipped::start`). Do not take: compiler-rt and libc pieces built from source on each machine's first use; here they are records.
- **Go** (memory: `cmd/go/internal/toolchain/select.go`; the `toolchain` line of `go.mod`; Go 1.20's removal of prebuilt `$GOROOT/pkg`). Take: the toolchain is a dependency, fetched as a module and checked by the same sum file as any module; and std is not a shipped artifact, only entries of the one build cache. Do not take: the cache starts empty on a new machine.
- **Nix** (memory: fixed-output derivations, Dolstra's thesis ch. 5; `scanForReferences` in libstore). Take: an outside byte enters only under a hash declared before the fetch; and outputs are scanned for the paths of their inputs. Do not take: absolute store paths as identity, and wrappers that add flags from the environment (observed here: a nixpkgs cc wrapper baked a build directory into a RUNPATH; nix's libclang has no default include path, `agents/annoyances/real-3.json`).
- Not taken from **rules_rust** and **`-Zbuild-std`** (memory; `core/compiler/standard_lib.rs` is what `blaze-units/src/stdlib.rs` follows): std as crate-grain artifacts keyed by the whole toolchain version and flag set, so a bump or a flag remakes all of it.

## 3. blaze today

**Shape (read).** The pin is `harness/toolchain` (`nightly-2026-10-27`). `toolchain::ensure` (`blaze-cargo/src/toolchain.rs:123`) downloads the upstream nightly's `rustc`, `cargo`, the host's `rust-std` and wasm32-wasip1's from static.rust-lang.org by sha256 (`toolchain/own.rs:31`, `pins.txt`) into `~/.blaze/toolchains`. std's source is blaze's `library/`, found by `library/DIGEST` and copied or downloaded to `~/.blaze/library/<digest>` (`toolchain/library.rs:119-205`). std is planned as cargo's `-Zbuild-std` plans it and keyed by `StdKey` (`blaze-units/src/query.rs:786`, `load/units.rs:1025`), its units kept in a second store `<machine>/std/<makers>` (`serve.rs:1195`). bstd is `crates/blaze-std` (lib `bstd`, 13,822 lines; 17 workspace crates, `http`, `miniz_oxide` and four `objc2` crates as dependencies). The edition is `edition::BlazeEdition` (`crates/edition/src/lib.rs:107`) turned into a crate attribute; syntax extensions are a `u8` set in every parse key (`Extensions`, `:213`; firewall `base-db/src/extensions.rs:42`). Links ask the machine's C driver (`blaze-link/src/target.rs:1418` `c_driver`, `:1444` `linker_dirs`, `:1572` `apple`, `:1617` `msvc`) unless the link is of Rust alone (`Target::ships`, `:811`). A native prefix is a pinned input (`blaze-units/src/load/native.rs`, `serve/native.rs`, `~/.blaze/native/sha256-<hex>`). The thin launcher finds a workspace's pin (`blaze-thin/src/pin.rs`) and runs `~/.blaze/versions/<v>/blaze` (`blaze-engine/src/pin.rs:428`).

**Measured.** bstd hello-world cold: 72.6 s, 257 units, all std's and bstd's closure, on every new home (brief). A store copied to a second checkout: 0 unit misses, 6.8 s against 23.8 s (brief). Three targets built from a clean environment and ran (brief; `scripts/src/bin/cross.rs`). Setting `LIBCLANG_PATH` once invalidated the whole cache (brief). 80 registry crates' images refused because fetched sources live under the daemon's home (brief). The Mac's `blaze` on PATH rejects `blaze-2026.11`; the integration build accepts it (brief). A bump takes 2 h 45 min to merge on a green day (docs/toolchain.md, 2026-10-27). **Read:** the Mac's nightly download is 116 MB (`pins.txt` sizes), of which `rustc` and `cargo` (60 MB) are "not read by v2's daemon at all" (toolchain-c.md); the engine binary is 302 MB (toolchain-c.md).

**Smells under rule 66.**
1. *Five mechanisms for one job* (fetch a pinned tree, check it, lay it out, keep it): `own.rs:256` `fetch_from` (file lock, staging, rename), `library.rs:205` `fetch_into`, `serve/native.rs` layouts with a `.blaze-native` mark, `blaze-engine/src/pin.rs` `versions`, and registry sources in `sources/`; each with its own directory outside any collector (disk.md smell 10) and its own hash (sha256 of an archive, sha256 of a line per file, BLAKE3 of files).
2. *Retry.* `TRIES = 4` in `own.rs:35` and `library.rs:47` (rule 3).
3. *A per-library key.* `StdKey` holds the whole library's root, the profile's *name* (`:793`), `host` (`:806`), the whole `rustflags` list (`:811`) and `macro_wasm`; one changed std file or one flag makes every std record another's. A std for `x86_64-linux` planned on a Mac and one planned on Linux differ by key whatever their bytes.
4. *A per-machine key.* `runs_here` (`query.rs:824`, `schema.rs:87`): a dev build's std is "compiled for this machine's own CPU"; `host_features` (`hir-ty-codegen/v2/toolchain.rs:471`) probes the CPU with `is_x86_feature_detected!`. A record made on CI is a hit on a laptop only when the two CPUs report the same list.
5. *A per-binary key.* `std/<makers>` names the store by `RecordMakers` (front end, codegen and record code of the whole binary), so each day's blaze reads none of yesterday's std (also disk.md smell 5).
6. *Unkeyed inputs listed by hand.* `blaze-codegen-code/src/lib.rs:706` `unkeyed_env`: `CC`, `CFLAGS`, `SDKROOT` and 13 more names, with their per-target and `HOST_`/`TARGET_` forms, are "no input" by a list; the files a C driver names are hashed, the driver is not.
7. *The machine decides a link.* `c_driver` reads `$CC_<triple>`, `$CC`, else `cc`; `linker_dirs` runs `cc -###` and takes `NIX_LDFLAGS`/`LIBRARY_PATH` directories; `newest_kit` takes the newest Windows kit installed.
8. *Switches that outlive their build.* `ready::BSTD_IN_TREE`, `ready::EDITION_SHIPS` (`blaze-lint-defs/src/ready.rs:42,51`), `blaze_new::BSTD_SHIPS`, `blaze new --bstd <PATH>`: bstd is found by a path a person gives.
9. *A per-crate key for an edition.* The edition is a crate attribute hashed into the crate's key ("no query result, record or object is shared between a crate with it and one without", std.md); 57 uses of `blaze_edition` in 16 files branch on the crate (counted by `rg`).
10. *Process globals with IO behind them.* `toolchain::FOUND` (`toolchain.rs:146`), `library::FOUND`/`FETCHED` (`library.rs:91,98`): found on disk once, fixed for the process.
11. *Enforcement in one command only.* `Vec::new()` builds under the bstd edition; only `blaze check` refuses it (measured, brief; std.md S5g). bstd's own tree has 36 warnings (measured, brief).

## 4. The end state (design)

**One sentence.** There is no toolchain directory and no std build: there are pinned **trees** (source and tools) and **records** (results), all found by content keys through the one store, and a first build asks for the same records by the same route as the thousandth.

**4.1 Trees: one way anything outside the binary arrives.** A tree is a store record (a listing of `(path, kind, BLAKE3, len)`, files as chunked values), named by its BLAKE3. `library/`, bstd's source closure, registry crate sources, `blaze-cc` (clang, lld, llvm-ar, compiler-rt, libc++, libclang), one C sysroot per target (headers, abilist, wasi-libc), the LLVM prefix blaze itself links, and a blaze release are all trees. One sans-IO machine fetches them (`blaze-fetch/src/verified.rs`, which exists with its simulation), one call places them read-only by clone, and one collector root holds them (disk.md 4.2 "named pins"). Pins are data in two places only: `toolchain.pins`, a record compiled into the binary (name, target, tree key, length) for what blaze ships, and `blaze.lock` rows for what a workspace adds (`native.*`, `tools.*`, `blaze = { version, head }`). BLAKE3 everywhere blaze publishes; sha256 stays only where a third party publishes it (a crates.io checksum).

**4.2 Virtual roots.** A tree is mounted, in the VFS and in every sandbox, at a path that is a function of what it is: `/rustc/<commit>/library` (as today), `/blaze/bstd/<version>`, `/blaze/registry/<name>-<version>`, `/blaze/cc`, `/blaze/sysroot/<target>`, and a checkout's packages at `/blaze/ws/<path in workspace>`. No query, key, diagnostic span or debug path sees where the bytes are on disk. On Linux the sandbox does this with a mount namespace. This removes the home-path refusal (80 crates) as a class and is what makes a build-script run's record portable.

**4.3 What is keyed by what** (so CI's record is a laptop's hit). There is no `StdKey`; std and bstd are crates under a root, and every record is at the grain end-state.md already names.

| Record | Key | Reads (each with its digest) |
|---|---|---|
| a file's item index | file content | — |
| a quiet crate's def map | its files' ids, its syntax bits | each `cfg` atom asked, dependencies' export digests |
| an item or function step (signature, inference, borrow check, MIR) | the parse-level key (text with bodies cut, names closure), the step's code id | facts of other items, each `cfg` atom, each target fact (`pointer_width`, `endian`, `has_atomic(n)`), each feature bit |
| an instance's code | the MIR record's key, type arguments, the code settings *as values* (opt level, debug assertions, overflow checks, panic strategy, debuginfo level, the target-feature set), backend and its code id | callee facts; a file-name record per position kept |
| a build-script or expander run | the program's record key, its arguments | each tool, variable, file and listing it asked (outside.md's one read form) |

Never in a key: a path on disk; the triple as a string where the facts it stands for are what was read; the host, for a record of target code; a profile's name; the whole `rustflags` list (it is parsed once into cfg atoms, features and settings, each read alone); the making binary (a step's code id, kernel.md's `Identity.code`, takes its place); a CPU probe. **The CPU** is a named level in the settings (`baseline`, `x86-64-v3`, ...), default `baseline` for every profile; `-C target-cpu=native` resolves to a feature set that is a read of the request. `Runs::Here` goes.

**4.4 The first build of a new project.** State machine of the launcher on a machine: `NoRelease → HeadKnown (signed head read) → Placed (engine tree placed; the host target's toolchain and bstd extents renamed into the store as a read-only layer, disk.md 4.6)`. Nothing else is fetched at install; `blaze-cc`, another target's extents and the common-dependency filters are fetched on first ask, in a span naming them. A build then resolves the user's crate; every ask about a std or bstd item is a `get(key)` that hits the layer; the instances the program reaches hit; the program manifest and link are the only work. "Compiles nothing" is a count: **0 records made whose source root is a toolchain tree**. A miss there (a `cfg` or setting the release did not build) is legal and is the same route: that one item is made, lazily, and kept; there is no prebuilt-std switch and no fallback (rule 3). What a release publishes is not a list: it is every record the release train's own builds made (the hello-worlds, bstd's tests, the real projects it already builds), per kept target, for `dev` and `release` settings, plus the wasm32-wasip1 std and the compiled expander modules of the proc-macro crates those projects use. A team's CI publishes the same way under its own key; that is "general to any crate dependency".

**4.5 Trust, in one rule.** Bytes are taken only when they hash to what a saying names, from any source (R2, a share, a peer: sources are untrusted); a saying is believed only when the blaze binary holds its hash (`toolchain.pins`: trusting it is trusting the binary) or a key the user listed signed it (the release key compiled in, a team's CI key). A record's truth is its signer's claim; rule 25 makes a sampled rebuild-and-compare the audit (disk.md 4.6).

**4.6 C inputs and `-sys` crates: a tool table, not an environment.** A workspace has one **tool table** record: blaze's defaults (`cc`, `c++`, `ar`, `ranlib`, `libclang`, each a path inside `/blaze/cc`, and the target's sysroot) plus the manifest's `[workspace.metadata.blaze.native.*]` and `tools.*` rows (each a pinned tree and the variable it answers). A build script's sandbox has: a `PATH` of the table's tools only; `CC`, `CXX`, `AR` and their per-target forms, `LIBCLANG_PATH`, `CLANG_PATH`, `BINDGEN_EXTRA_CLANG_ARGS_<target>` (`--sysroot=/blaze/sysroot/<target>` and clang's resource directory), `PKG_CONFIG_LIBDIR` (empty) answered **from the table**. The read recorded is `(tool row, tree key)`. A variable of that family in the user's shell is not an input of anything: it is said once, naming the manifest row that would change it. So setting `LIBCLANG_PATH` remakes nothing, and bindgen finds `assert.h` with no setting. A script that runs a program the table lacks (cmake, perl, make) fails naming the program, the package and the row to add (`tools.cmake = { pin = .. }`, or `system = ["cmake"]`, which keys the machine's binary by its hash and traces what it reads, making those records this machine's). The macOS SDK stays the vendor's (license, toolchain-c.md): each file read from it is a read with its digest. Links are blaze-link's, in process, from the sysroot tree (stubs made in memory from the abilist, the start object from `shipped::start`); an rpath is written only from a declared input. On macOS, where a sandbox cannot rename paths, a run's roots' real paths are reads of the run (question 7.4).

**4.7 Updates.** *The nightly bump* stays a daily merge of `library/`. By keys it remakes: items of `library/` whose parse-level key moved; readers of a fact that moved; records of a step whose code moved. Two things that would otherwise touch everything are made narrow reads: the `/rustc/<commit>/` prefix (a file's name string is its own record, read only by instances that keep a position, so a new commit remakes one name string a file (`library/` has 3,130 `.rs` files, counted), not code) and the version string (a read of the scripts that ask `rustc --version`; their output is unchanged, so their readers stop there). *A blaze release* is a head: `(version, engine tree, extents)`. For published packs the key directory is an extent of its own and values are addressed by content, so a release whose step code ids moved while its values did not ships a new directory and no values (Mokhov et al.'s constructive trace: key → value hash). This is one requirement on disk.md 4.4, whose batch keeps keys beside values. The engine binary travels as FastCDC chunks (survives, disk.md). `blaze.lock` records the head's BLAKE3 beside the version (Go's sum for a toolchain); the thin launcher fetches a pinned release it lacks through the same fetcher, bounded, with one typed failure. The installer installs the launcher and nothing else. The nightly download from static.rust-lang.org is deleted (toolchain-c.md slice 7).

**4.8 Editions and extensions: one front end, bits read as facts.** A crate has one `Features` input (Rust edition, blaze edition, extension bits, unstable features). A blaze edition is a *named set of bits* and a prelude name, nothing more; no code branches on "is this crate of the edition". Three kinds of reader, each exact: (1) the lexer and parser read the syntax bits, carried per token by the crate that wrote it (Rust's edition hygiene; `uniq_in_a_macro_is_read_under_the_gate_of_the_crate_that_wrote_it` exists); a parse is keyed by text and syntax bits, but an item's key is over its tokens, so a crate that turns on a bit it never writes moves no item key. (2) Name resolution reads one fact, `std_of(crate)` (Rust's std or bstd) and the prelude. (3) A per-function step reads `feature(crate, bit)` like any fact (handles, early drop, effects, linear, the global-heap refusal), so opting in redoes exactly the functions whose steps read a bit that changed. Enforcement lives in the queries every command runs: `Vec::new()` under the edition is refused by `build`, `run` and `check` alike (S5g becomes the one walk). The no-change rule is a gate check, not a review: the Rust-edition fixture corpus's record keys under a blaze with every extension compiled in equal a golden list, and a census asserts no blaze bit was read true. `blaze::not_latest_edition` stays one finding a package. `blaze new` writes the edition *and* the blaze pin; a manifest naming a blaze edition this blaze does not know is an error naming the pin line to add (the measured PATH mismatch). An analysis extension (extensions.md) is a crate built against the `blaze-ext` tree like any other; its records publish like any other.

**4.9 bstd as "just a crate".** bstd is found the way std is: a tree at `/blaze/bstd/<version>` named by `toolchain.pins`, no dependency line, no `--bstd`. Its build must have: no build script and no proc macro anywhere in its closure (reflection, rule 56), held by a test that walks the closure; no cargo features (one configuration, so one set of records); platform code split by `cfg` atoms only; no workspace-inherited manifest keys in what is published; zero warnings in the gate (36 today); every global-heap line gone by S4 (128 today, read std.md). Its closure is then data like `library/`, its records ride the same extents, and the edition's `std_of` fact is the only place it is named.

**4.10 Memory and state.** Nothing of the toolchain is held between requests: roots are fields of the plan record (end-state review point 3); tree listings and records are read through the pool; the fetch machine's buffers live in the fetching task's frame.

**Rules.** 3: one fetch attempt per source with strikes inside `verified`, no `TRIES`; an unknown tool, edition or missing extent is an error naming it. 9/10: scripts and expanders see only virtual roots and the tool table; expanders are wasm records. 14: the fetch, the launcher's state machine and the tool-table resolution are cores; `toolchain::FOUND` and its kin go. 21/65: 4.3. 25: virtual roots, a fixed tool set and sorted listings make two machines' outputs one byte string; `cross.rs`'s `expect` hashes test it. 43: the launcher's install and a release switch get a DST (crash at any step leaves the old release runnable). 51: trees and pins are records. 5 (useful-not-parity): `/rustc/<commit>/library` is kept only because debuggers and IDEs map it.

**Where the one idea needs a second clause here.** "A record holds when its reads hold" assumes the maker was this machine. For a fetched record the reads still decide validity, but its truth rests on 4.5; that clause belongs beside the idea, not in each area.

**4.11 Cut from scope.** Hosts kept: aarch64-apple-darwin, aarch64-unknown-linux-gnu, x86_64-unknown-linux-gnu. Targets kept: those three, wasm32-wasip1 (expanders and scripts only), `wasm64-blaze-wasip1` and the GPU target as they are; queued, in this order: bare-metal AArch64 (core and alloc only, no C library: nothing new in this design), then musl (needs a static ELF writer). Cut and deleted until asked for: Windows as host and target (`msvc`, `newest_kit`, `x86_64-pc-windows-msvc` in `pins.txt`), x86_64-apple-darwin, sanitizer runtimes until compiler-rt comes from `blaze-cc`, a per-workspace glibc release (2.28 fixed), `-Zbuild-std`'s crate and feature flags as a surface (a `cfg` miss already compiles what is reached).

## 7. Unsound, unknown, or to measure first

1. **How much of std carries across a bump?** Diff the parse-level keys of `library/` between two snapshots of `upstream/library`; if most items move daily, 4.7's saving is only in fetch, not in work.
2. **Are step code ids stable across releases, and do they exist while cargo builds blaze (D25)?** Compare `fn_info(..).code_id` of the lowering, inference and codegen steps between two release builds. If they move daily, every key moves daily and step 6's directory split is what makes updates cheap; if they do not exist under cargo, the release must stamp them another way, stated.
3. **How big are the extents?** `du` of the copied store that gave 0 misses, per target and setting; the bar is `rust-std`'s 30.9 MB (read, `pins.txt`).
4. **macOS has no path-renaming sandbox.** Is there a fixed root every Mac can have without root rights? If not, a Mac's script-run records are keyed by their roots' real paths and are shared only between equal paths (CI runners). Measure on reth: script outputs that differ between two home paths with prefix maps on.
5. **Which generic instances to publish?** Build reth against a pack made without reth and count instance hits; that is the real "common dependencies" number.
6. **Is anything lost by `baseline` in dev?** Run reth's tests at baseline and at the host's features; if the gap matters, the level becomes a workspace setting published as a second pack.
7. **libclang from blaze's LLVM**: `llvm.py` makes one static archive; bindgen needs a shared `libclang` matching `clang-sys`. Build it on the three hosts and run `reth-mdbx-sys`'s script.
8. **Expander purity**: a published expansion record needs the rule end-state.md's open question 4 leaves open.
9. **Owner's**: the release signing key; whether `libSystem.tbd`'s list may ship; whether a fetch-on-miss may send keys of private code to a listed source.

## 8. How to cut it (builders with 200K tokens, no compiler)

- **One mind:** the key table of 4.3 (what leaves `StdKey` and where each field goes) and the tool-table schema; then step 1's change to `blaze-units/src/query.rs` and `load/units.rs`, since every std caller reads them.
- **Whole in a few files each, parallel after that:** (a) `toolchain/trees.rs` (pins, place) replacing `own.rs`, `library.rs` and `serve/native.rs`'s layout, with the fetch core's simulation; (b) the launcher's install machine and its DST (`blaze-thin/src/pin.rs`, `blaze-engine/src/pin.rs`); (c) the tool table and the script environment (`blaze-build-script` `env.rs`, `blaze-usercode/src/script.rs`); (d) `blaze-link/src/target.rs`: sysroot-tree reader, deletion of `c_driver`/`linker_dirs`/`msvc`; (e) `Features` and the `feature` fact (`crates/edition`, `base-db/src/extensions.rs`), then one crate of readers at a time; (f) the virtual-root mounts for registry sources and bstd (`blaze-units/src/stdlib.rs`, `load`); (g) bstd's closure test and warning cleanup; (h) `llvm.py --cc` and the train's publish step (scripts; no compiled code).
- **Must not be split:** the removal of `runs_here` (plan, std key and code generator read one rule), and the switch of std from `StdGraph` to plain crates under a root.
