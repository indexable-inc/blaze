# Building, testing and measuring blaze

## blaze-builds-blaze (rule 2)

Interim, by the owner's decision of 2026-11-11: blaze's own tree is built, checked and unit-tested
in the dev loop with cargo and the pinned nightly (`harness/toolchain`): `cargo +nightly-<date>
check -p blaze-engine`, `cargo +nightly-<date> build --release -p blaze-engine`, with
`LLVM_SYS_231_PREFIX` naming the LLVM `crates/hir-ty-codegen/llvm.json` pins (blaze's own copy under
`~/.blaze/native/` serves). On 2026-11-11 that check took under two minutes and a release build 292
s on an 18-core Mac, where blaze building blaze took about 80 minutes and 175 GB on 64 cores. A
blaze cargo built is a legal stage 0 and the daily driver. What does not change: blaze must keep
building blaze (a self-build runs at least daily and before a release, and a release binary is one
blaze built, stage 2 equal to stage 3); a claim about what blaze does (it builds a project, an edit
takes so long, a test passes under it) is measured with a blaze, never with cargo standing in for
it; and a failure of blaze on blaze (a compile error, a panic, too slow, too much memory) is ranked
work, never dropped because cargo got past it. The tree stays accepted by both compilers while this
holds: attribute-form extensions (`#[blaze::pure]`, `#![blaze::sans_io]`, tool attributes rustc
ignores) are used as before, and code only blaze accepts (a borrow rustc refuses, extension syntax)
waits or sits behind the extension's own crate; where the two disagree on plain Rust, rustc's
refusal of a program blaze accepted is a blaze bug to file (2026-11-11: a method redeclaring its
impl's lifetime). The rule returns to blaze-only when the owner says the loop is fast enough; the
measure to watch is a warm rebuild of blaze by blaze after a one-function change in under a minute,
and a cold one inside 64 GiB. Never sccache.

See [docs/contributing.md](../../../docs/contributing.md).

## verify-on-real-projects (rule 7)

A verdict on blaze comes from real projects built by blaze: blaze itself, then large open-source
workspaces (ripgrep, nushell, bevy, wasmtime, tokio, ...), each built with `blaze build` and its own
tests run with `blaze test`. A project whose tests pass under blaze is correct for what they cover;
a failing test is a blaze bug to fix. Never build a project with rustc or cargo to diff against: no
reference build, no output comparison with rustc's, no harness that runs cargo for an oracle. A
test's expectation states what is right, not what rustc printed.

See [docs/harness.md](../../../docs/harness.md).

## own-nightly (rule 8)

blaze is its own toolchain: it builds every project with its pinned nightly (`harness/toolchain`,
bumped daily), ignoring rust-toolchain files, rustup, `RUSTUP_TOOLCHAIN` and `RUSTC`. Projects pin
the blaze version, not Rust's.

See [docs/toolchain.md](../../../docs/toolchain.md).

## measure-the-exact-tree (rule 22)

A measurement, bisect or checkpoint names the exact tree it ran on (a content digest of the sources
and the blaze binary's hash) and keeps that tree; never re-sync or rebuild between measuring and
committing. A result you can't tie to a tree is not evidence.

## work-in-ix-vms (rule 34)

There is one ix VM for all of blaze's work: `blaze-vm` (arm64, 128 cores, 256 GiB committed; how-to
`H12` under `agents/howto/` has its layout and how to remake it). Builds, tests, benchmarks,
real-project runs and experiments on Linux all run there: nobody makes another VM (`ix new`) for a
lane, a measurement or a project. It holds the one tree at `/root/blaze` with a warm build; blaze is
built only through `/root/loop.sh <branch> <command...>`, which takes a lock, checks out the branch,
builds once, installs to `/root/inst` and runs the command (ten minutes at most inside the lock); a
lane's own state lives under `/root/wt/<lane>/` and long runs are systemd units it polls. Because
every lane shares the machine, a timing names the load average it was taken under and compares base
and new alternately in one window; for a table a claim rests on, the main agent holds the other work
and the row says so. The exceptions are facts the one VM cannot give, each named in the lane's brief
with its reason: an x86_64 or other-architecture machine to RUN binaries on (never to build), and
the Mac for macOS behaviour (one build at a time, since three at once made every number of a night
unusable). Never AWS (`fleet-ops`, `dev-aws-N`). Where none of these can do it, stop and say what is
missing.

See [docs/contributing.md#working-in-parallel](../../../docs/contributing.md#working-in-parallel).

## fan-out-write-only (rule 35)

There is one integration tree (branch `int-<date>`, main plus every lane's pushed branch) and one
build VM that holds it with a warm build, so a merge costs an incremental build, not a cold one. A
lane has its paths in the one integration directory and nothing else (`worktree-per-lane` says when
a worktree is right instead): it reads and writes code and tests there and never makes a VM
(`work-in-ix-vms`: there is one, `blaze-vm`), runs cargo or blaze on its own, or starts a daemon of
its own; it says plainly what it has not run. A lane that must see its code run asks the one queue:
`ix shell blaze-vm --noninteractive -- /root/loop.sh <branch> <command...>` builds the pushed branch
in the one tree and runs the command with that binary. The main agent runs the integration loop
(`harness/v2/integrate.py`, one JSON value naming the branches): fetch, merge each branch (a branch
that conflicts is left out and named), one build, then every check at once on that one binary: the
edit-loop table beside the reference, the stale-answer run, new project, restart, memory, disk, the
revision tests and the unit tests of the crates touched. One table comes out, tied to the tree's
commit. A build error or failed check goes back to the lane whose files it names, with the tree, the
command and the output; the lane fixes and pushes, and the loop runs again. A lane that needs to see
something at run time asks for it as a check added to the loop (a script, a test, a span query), or
is given the loop's built binary and its own `BLAZE_HOME` on the build VM to run read-only
experiments; it does not build its own copy. What only one lane's change can show (a causal claim,
`test-the-cause`) is run by the main agent as a patch on the tree. Landing: main takes the
integration tree, or a branch of it, when the table and the tests are clean on that exact commit.
Exceptions are named in the lane's brief with the reason: work that cannot share the VM (a benchmark
that needs quiet cores gets a VM of its own; a macOS-only fact is measured on the Mac, one build at
a time).

## worktree-per-lane (rule 36)

The default is one directory: the integration checkout on the Mac (how-to `H12` under
`agents/howto/` names it), on the integration branch. Every lane edits there, within the paths its
brief gives it, and does not run git: the main agent commits (one commit per lane's piece, crediting
it), pushes, and has the one VM build and test the whole tree at once. A lane says when its piece is
ready to be built and what test shows it; until then its half-written files must not break the build
for the others (add new code beside the old and switch over last, or keep it behind a module that is
not yet referenced). Two lanes never write the same file: the brief's paths say who owns what, and a
lane that needs a line in another's file asks the main agent. A worktree (uniquely named, with its
own branch) is for the cases the one directory cannot serve: two lanes that must rewrite the same
file, a bisect or a causal test that needs a variant tree, a long-lived rewrite that cannot keep the
tree building; the brief says which. Never `git stash`: it is one stack shared by every worktree.

## clean-up-lane (rule 39)

When a lane is done, delete what it made: its directory under `/root/wt/<lane>/` and its homes on
`blaze-vm`, any daemons it started there (by pid), any worktree and merged branch, and any exception
machine its brief allowed (`ix rm`). The build VM itself is never removed by a lane.

## ledger-decides (rule 46)

The ledger is `docs/v2/plan/objectives.json`, one row per objective: the outcome, the check that
decides it as a command, its paths, its status (`docs/v2/plan/objectives.md` is its generated
table). `scripts/src/bin/ledger.rs` (`blaze run -q -p scripts --bin ledger -- '<json>'`) picks work
that does not collide (`pick`), runs a row's check and writes its status with the commit (`run`),
and regenerates the table (`write`); never type a status by hand, except `blocked` with why. Before
starting a row, run its check on main. A row with no check gets one written first, as part of the
work. Done means the check passes on a named commit and has joined the gate or the release train, so
it cannot regress silently. A row that fails twice records what blocks it and stops.

See [docs/v2/plan.md#how-the-work-is-run](../../../docs/v2/plan.md#how-the-work-is-run).

## every-agent-has-a-task (rule 47)

Start an agent only with a task: an objective's id from the ledger, or a named piece of one, with
its outcome and its check in one line each, the paths it may touch and what done prints. A sub-agent
takes its parent's task unless given its own. The agent app's sidebar lists tasks with their agents
under them, so name the task for a person reading that list: what is being done, not who does it.

See [docs/v2/plan/design/tasks.md](../../../docs/v2/plan/design/tasks.md).

## agents-are-a-cost (rule 48)

An agent costs its whole context, and its report loses detail both ways, so the coordinator does
small pieces, reads and deletions itself and never starts a fleet to read or summarise. But work
that splits into independent, large pieces is done in parallel, all of it at once (`sota-first`):
one lane per piece, each with its own worktree and a brief that states its outcome and check, as
many as the work has independent pieces and the machines can build. What bounds the number is
independence (two lanes in one file cost more than they save) and the coordinator's ability to merge
and verify what comes back, not a fixed count. Do not give one lane a numbered list of pieces that
do not depend on each other: it will do the first and the rest wait unstarted for hours. When you
write such a list, ask of each item whether it needs another item's result; each one that does not
is its own lane, started in the same message, with its own files (`worktree-per-lane` says how lanes
share one directory) and its own check. The same holds for you: when you say a piece is "queued",
"next" or "when a lane frees up", and nothing it needs is missing, start it instead. What bounds the
number of lanes is what can actually run at once (builds on the one VM, files that would collide,
your ability to merge and check what comes back), not a count; say which of those is the limit when
you hold something back. Review the lanes' lists when they report: a "not started" item that could
have run beside the others is moved to a lane of its own at once.

See [docs/v2/plan.md#how-the-work-is-run Andrew, 2026-11-12, on hearing that four of the five pieces of the content-keyed store were "not started" after two hours because one lane held all five in order: "mention in AGENTS.md: if something can be done in parallel, do it instead of waiting for it to start (and here do them in parallel, as you said, not started)".](../../../docs/v2/plan.md#how-the-work-is-run Andrew, 2026-11-12, on hearing that four of the five pieces of the content-keyed store were "not started" after two hours because one lane held all five in order: "mention in AGENTS.md: if something can be done in parallel, do it instead of waiting for it to start (and here do them in parallel, as you said, not started)".).

## How a lane runs

From [docs/contributing.md#working-in-parallel](../../../docs/contributing.md#working-in-parallel):

- Worktree: `git worktree add -b <branch> ../blaze-<lane>-<date> origin/main`. Commit work in
  progress to the lane's branch instead of stashing.
- VM: `ix new --name <lane> --no-shell` (`--cpus`, `--memory`, `--memory-commit` for a build,
  `--arch x86_64|arm64`, `--ttl 8h`); run with `ix shell <lane> -- <command>`; send a checkout with
  `git bundle create - <branch> | ix shell <lane> -- bash -c 'cat > src.bundle && git clone -b <branch> src.bundle src'`.
  The VM has no GitHub or AWS credentials. A benchmark gets its own VM pinned to a host CPU class
  (`--cpu epyc-5`, `xeon-6` or `graviton-5`) with `--memory-commit`.
- The central loop, run once by the main agent on the combined tree: `blaze check` then
  `blaze test`, keep-going (the default), every failure handed back with the tree, command and error.
- Checking agents' work fast, per commit, without waiting for the build
  ([docs/contributing.md#checking-a-change-fast](../../../docs/contributing.md#checking-a-change-fast)):
  `blaze check $(blaze run -q -p scripts --bin changed -- '{"base": "<the commit before>", "print": "args"}') --lib --tests`
  in the lane's VM, in parallel with the build. `changed` prints the packages the commit
  touched and their dependents in the order to check; hand the first error back to the agent
  that wrote the code. Never let thousands of lines pile up unchecked behind an hour-long build.
- A lane script, a harness and your own loop check every command's exit status and stop at the
  first failure (`set -euo pipefail`; `check=True`), unless the line says why not. A command
  that does not exist (`blaze daemon stop`; it is `blaze stop`) exits 101 and a script that
  goes on measures nothing true
  ([docs/contributing.md#scripts-that-run-commands](../../../docs/contributing.md#scripts-that-run-commands)).
- The gate holds the budget smoke's guards
  ([docs/harness.md#the-smokes-guards](../../../docs/harness.md#the-smokes-guards)): run
  `uv run --frozen python harness/v2/budgets.py '{"command": "smoke", "engine": {"kind": "v2", "blaze": "<built blaze>"}}'`
  on the built blaze before landing anything that touches the daemon, the plane, the front end
  or the store; a guard that fails is fixed, or recorded with its cause (`"record": true`).
- Run harnesses with `RUST_BACKTRACE=0`.
- Done: `blaze clean` in the worktree, `git worktree remove <dir>`, `ix rm <lane>`,
  `git branch -D <branch>` once merged.
