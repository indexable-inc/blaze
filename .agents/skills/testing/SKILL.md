# Testing blaze

## test-the-cause (rule 23)

A causal claim (this change caused the regression, this lock causes the convoy, this index makes it
fast) is tested by removing the cause and watching the effect go, not by checking that its premises
hold. Pin a load-bearing one with a test named for the property.

## persisted-state-round-trips (rule 26)

Anything blaze persists (the store's records, the certificate, the profile history, and the daemon
image while it exists; what a persisted value is, is `outputs-are-records`) has a test that restores
it and checks the result equals a fresh build byte for byte, and a budget for a fresh process to
first answer. A file that another version of blaze can find (in the state directory, in a home, in
`/tmp`) also has a test that a file of its previous layout is handled: an old home after an upgrade
is detected, reported by name and rebuilt, and nothing is migrated (scope decision D36); a file
outside a home is refused by name with what to do, or left alone under a name that carries its
layout; docs/cargo.md, "Files that outlive a version", lists each with its test. A restore that
silently starts empty is a failure blaze reports, naming why. A format that is written while blaze
runs and read after a crash also gets a DST (`dst-not-review`) that crashes it at every point and
checks the restore.

## dst-not-review (rule 43)

Code that is concurrent (atomics, locks, lock-free rings, two threads or processes sharing state),
durable (anything written to disk that must survive), crash-recovering, billing or data-deleting is
proven by a deterministic simulation test (DST): one test on blaze's own engine (`blaze_sim::check`)
that draws an operation sequence, the fault classes to turn on, crash points and schedules from one
tape, runs the code as a sans-IO core in the simulation (`blaze_core::sim::Sim` for blaze-core's
effects; `blaze-check` where two threads' atomics must interleave), and checks an oracle that states
the invariant ("every row recorded appears exactly once after any crash"), with planted-bug controls
the oracle must catch and a failing tape that replays. A code review is not evidence that such code
is right: it finds candidates, and each one it finds becomes a case the DST must catch before the
fix lands. A change to such code without a DST that covers it is unfinished, whoever reviewed it.

## invariants-are-stated (rule 53)

What code must always do is written once, in blaze, and every check reads the same text. A contract
(`requires`, `ensures`) says what one call does. A reference model is a small, pure, sequential
implementation of what a component means, an ordinary type in the crate under `/// The reference
model:`. `/// The invariant:` goes on the test whose oracle checks an invariant, and `/// The
refinement:` on the test that runs an implementation against its model (or another implementation)
and compares. Each needs a control in the same file, a test named `the_oracle_catches_<the planted
bug>`. The statement then climbs a ladder without being rewritten: tested (a property test),
simulated (the deterministic simulation with faults and crashes), model-checked (every interleaving
to a bound), proved (Lean, from the same contract and model; say it as `/// The invariant (proved:
<proof file>):`). Durable, concurrent and crash-recovering code is at least simulated; prove the
sans-IO cores and what must never be wrong; a disagreement between two levels is a bug in one of
them. `scripts/src/bin/invariants.rs` (`blaze run -q -p scripts --bin invariants -- '<json>'`)
collects every statement with its level into `docs/v2/plan/invariants.md` (`write`) and fails the
gate (`check`) when one has no control, names a missing proof, or the list is stale. Before changing
or regenerating code, read the invariants its crate states: they are what the new code is judged
against. A promise in a doc comment is either derived (an effect attribute the build checks) or a `#
Guarantees` / `# Invariants` item ending in ``Evidence: [`test`]``, ``Evidence: Lean `Name` `` or
`Unverified: why`; never prose alone. The `claims` lints refuse a doc the effect walk refutes, a
promise held by nothing and a stale pointer; the ledger refuses a crate's count of open claims
growing or any claim's level dropping (docs/v2/plan/design/claims.md).

See [docs/v2/plan.md#11-proof-by-check-not-by-review](../../../docs/v2/plan.md#11-proof-by-check-not-by-review).

## verified-compiler (rule 57)

blaze is to be a compiler whose correctness is proved, not only tested. The order that works in
practice: (1) one specification of what MIR does, written in Lean as an executable semantics (an
interpreter over a deep embedding of MIR), held to the tree by running it against blaze's MIR
evaluator and blaze-built code on generated programs; it is the one meaning every proof refers to
(`one-concept-one-home`); (2) user code is proved against it: the functional models `hir-ty-lean`
emits are derived from, and proved or checked equal to, the semantics of the body they model, so a
proof is about what blaze compiles and not a hand-written copy; (3) each MIR transformation is
correct against it: a small pass by a Lean theorem that its output refines its input, a large one by
translation validation (a checker, itself proved sound, that accepts each run's before and after),
run in the gate on real crates; (4) then lowering to LIR and to machine code against machine models,
the front end's rules, and the driver's state machines by refinement from their reference models
(`invariants-are-stated`). Nothing counts as proved until Lean has checked it in the gate with only
its allowed axioms and no `sorry`; `docs/v2/plan/invariants.md` gives each claim its level, and
docs/v2/plan/design/formal-verification.md lists the trusted base (the Lean kernel, the semantics'
agreement with hardware, each unverified pass) and shrinks it. A change to MIR's meaning changes the
Lean semantics in the same pull request.

See [docs/v2/plan/design/formal-verification.md](../../../docs/v2/plan/design/formal-verification.md).

## simulate-first (rule 64)

Default to the simulation. When you test behaviour over time (an edit after a build, a restart, a
crash, two requests at once, a file replaced under a watcher, a cache hit after a key change, a
retry, a timeout), write the test against the sans-IO core driven by `blaze_core::sim::Sim` (virtual
clock, simulated filesystem and network that can be slow, fail, tear or reorder, crashes at any
step), not against a spawned blaze process, real files, real sleeps or real threads. Such a test is
declarative (the steps and what must hold after each), runs under many seeds, prints the seed and
the step on failure so it replays exactly, checks an oracle that states the invariant, and has a
planted bug the oracle catches (`dst-not-review`). For incremental behaviour the shape is the
revision test: a small project and a sequence of source revisions with state kept between them,
asserting after each what was redone, what was reused, and that the result equals a clean build of
that revision byte for byte. Reach for a real process only for what a kernel alone can show (the
order file events really arrive in, executing a built program, signals, code signing, a real
socket), keep those tests few, and say in each which fact needed the real thing. When the code you
need to test cannot run under the simulation (it starts threads, opens sockets, reads the clock,
spawns a process or touches the filesystem directly), that is the finding: it breaks
`sans-io-cores`; cut the seam (a core with an injected effect interface and a thin driver) as part
of the change, or record exactly what blocks it and where, and do not paper over it with a slower,
flakier end-to-end test. A bug found by hand or in production gets a simulated reproduction before
its fix, minimized to the smallest revision sequence or transcript that shows it. Prefer a property
over examples, a reference model over assertions about internals, and comparison with a clean build
over expected output typed by hand.

This skill is the one home for how blaze tests its own code. Other skills and docs point here:
`build-and-test` says how tests are run (`blaze test`, the central loop, the main agent runs it),
`debugging` says how a cause is found from the profile, and `runtime-code` holds `sans-io-cores`,
which is this skill's precondition.

## Which test, and how many

Write few tests, each where it pays:

- **Hard-to-verify logic behind a stable interface** (billing math, durability ordering, data
  deletion, a key's coverage, a codec): a unit or property test beside the code. If the
  signature is still moving, don't write one yet; prove it end to end and come back.
- **Concurrent, durable, crash-recovering, billing or data-deleting code**: a deterministic
  simulation test (DST), below. This is the requirement of `dst-not-review`, not an option.
- **A bug found in a real crate**: that crate's own tests under `blaze test`
  (`verify-on-real-projects`); a daemon bug: a step in the edit harness
  ([docs/harness.md](../../../docs/harness.md#adding-a-test)).
- **A slow or flaky reproduction**: shrink it (blaze-sim's shrinker, treereduce, `git bisect`) into a
  test that runs in seconds, named for the property it breaks. That one is always allowed.
- **Parsers of hostile bytes**: fuzzing (`crates/blaze-fuzz`, `fuzz/`).

No big suites, no tests of code whose shape is still changing, no red/green ritual on a dev
host: push and let CI and the harnesses catch breakage.

## Property tests and simulations: `blaze-sim`

blaze owns its test engine (decision D37,
[docs/v2/plan/design/sim.md](../../../docs/v2/plan/design/sim.md)): `crates/blaze-sim`. A case is
a function of one tape of labelled, bounded choices in which 0 is the calm choice; the engine
draws tapes from fixed seeds, shrinks a failing tape to the fewest and smallest choices that
still fail, and prints one line that replays it.

- `blaze-sim.workspace = true` under `[dev-dependencies]`. A test is a plain `#[test]` that
  calls `blaze_sim::check(Config::cases(200), |tape| { .. })`; the body draws from `tape` and
  panics, or returns `Result<(), Broke>`.
- Every draw has a label, which a failure prints: `tape.below(n, "kill")`,
  `tape.int_in(1..=60, "size")`, `tape.coin("the sync fails")`, `tape.pick(&KINDS, "kind")`,
  `tape.vec(0..=40, "ops", op)`. A generator of a domain value is a function of the tape
  (`fn op(tape: &Tape) -> Op`). Make the calm choice the quiet one: no fault, the first
  alternative, the list ends.
- Seeds are fixed (256 from 0 unless the test says), so a green run is green again. From
  outside: `BLAZE_SIM_SEEDS=<n>` runs more, `BLAZE_SIM_SEED=<n>` one seed, and
  `BLAZE_SIM_TAPE='<tape>'` the tape a failure printed.
- A check fails by name when its cases drew nothing, were all discarded, or never reached a
  point it lists (`Config::must_reach`, `tape.reached(..)`). Mark the state a bug needs with a
  reach point, so a green run shows the run got there.
- Hegel is gone from the tree (ledger row V12): every property test and simulation is a
  `blaze_sim::check`. Never proptest, quickcheck, arbitrary or bolero.

## Deterministic simulation tests (DST)

A DST runs real blaze code (not a model of it) against a simulated machine whose every choice is
drawn: when a completion arrives, which effect fails, where the power goes out, which thread
runs next. The engine searches those choices, shrinks a failure to the smallest run that still
fails, and replays it exactly.

### What exists today: `blaze_core::sim::Sim`

`crates/blaze-core/src/sim.rs` is a seeded, single-threaded `Driver` for blaze-core's effects
(files, syncs, renames, watches, lists, processes, sockets):

- `Sim::new(seed, Faults { .. })`: a virtual clock (`advance`), completions delayed up to
  `max_latency` and delivered in a shuffled order, an effect failed once in `fail_one_in` (a
  failed append writes a random part of its bytes, a failed sync makes nothing durable), clones
  refused (`no_clone`, as on ext4), watch changes lost (`lose_change_one_in`).
- `crash()`: power loss. Everything in flight is gone; each file keeps what was synced plus a
  random prefix of the later changes, the last of which may be torn. A whole-file write or rename
  that completed is kept whole.
- Targeted faults: `fail_syncs`, `hold_syncs`/`release_held` (a commit that hangs), `slow_writes`,
  `hold_lists`/`fail_lists`, `hold_sends`, `lose_changes`, `fill` (a full disk: appends and
  writes under a directory past its room fail with ENOSPC, an append keeping the part that fit),
  and `record` to see the order completions were told in.
- A lock table for `Effect::Lock`/`Effect::Unlock` (flock's semantics, never waiting: a lock that
  another excludes is `Done::Contended`), with `hold_lock`/`release_lock` for another process's
  lock of a file; a crash lets every lock go, another process's too.
- `program` for spawned processes (a memory limit kills, as a cgroup does), `dial`/`peer_*` for a
  peer outside the simulation.
- Reads into and writes from memory the asker owns (`Effect::ReadInto`, `Effect::WriteFrom`),
  carried out against the registered memory itself (`blaze_core::Memory` for a test's own): a
  read scribbles its span with `sim::SCRIBBLE` at submit and fills it at completion, so a
  reader of a span in flight sees the scribble; a write takes its bytes from memory at
  completion, so memory changed in flight is what lands; a failed write, and one in flight at a
  crash, lands any of its 512-byte sectors, and a crash tears unsynced writes from memory by
  sector. Targeted: `hold_reads`/`release_reads`, `fail_reads`, `short_reads`, and `rot` (a
  block changed on disk under what was synced). `crates/blaze-core/src/sim/pages.rs` is the
  worked example: a pool-shaped page store, its oracle, five planted bugs and seed replay.

Examples: `crates/blaze-cas/src/tests/model_check.rs` (the store's operation sequence and the
`Sim` seed are drawn, and the store is checked against a `BTreeMap`) and the crash tests in
`crates/blaze-cas/src/tests.rs`; `crates/blaze-graph/src/sched/tests.rs` for the scheduler core.

Its limits: its own choices (latency, delivery order, what a crash tears) hang off one seed the
test draws, so a failure's plan is shrunk and its schedule is not, until `Sim` takes the tape;
it is one thread, so it interleaves a core's steps and the IO completions between them, not two
threads' atomics (that is `blaze-check`, next); it has one process and one version of the code;
and its file system is simpler than a kernel's (a completed whole-file write or rename is
durable).

### Interleaved atomics: `blaze-check`

`crates/blaze-check` is blaze's model checker for lock-free code
([docs/v2/plan/design/model-checker.md](../../../docs/v2/plan/design/model-checker.md)): under
`--cfg blaze_check` a crate's `sync.rs` hands out the checker's atomics, locks and threads, every
atomic operation is a switch point, and `blaze_check::model(..)` runs the schedules (every one
to a bound, or a sample) on one OS thread; `CHECK_REPLAY` reruns a failing one. Two atomics that
must move together, a ring, a table: a model test there, with its planted bug. It has no disk
and no crash: a structure that is both lock-free and durable is also stepped one atomic at a
time as an actor under `Sim`, until the two share a tape.

### Where it is going: one tape

[docs/v2/plan/design/sim.md](../../../docs/v2/plan/design/sim.md), in its order: `Sim`'s generator becomes the tape, so its latencies, delivery order, tears and
failures are shrunk with the plan; `blaze-check`'s sampled schedules draw from the tape, so one
case interleaves threads and crashes a disk; `Sim`'s disk takes the three-layer crash model (a
write durable only through a sync, a directory entry only through its directory's), with
several processes and two versions of the code on one disk. Until a piece lands, model what it
lacks in the test (draw which actor steps next; run the old and new codec against one simulated
disk).

### The recipe

1. **Make the code a sans-IO core** on blaze-core's effects (`sans-io-cores`): it reads time from
   the injected clock, hands back effects, and takes completions. A core that opens files,
   spawns threads or sleeps cannot be put in the simulation; making it a core is the first part
   of the change, not optional cleanup.
2. **Write one check** (`blaze_sim::check`) that draws everything from the tape:
   - the operation sequence (`tape.vec(1..=40, "ops", op)`: record, flush, merge, read, retire,
     restart, ...);
   - the fault classes to turn on, as a swarm: each run draws a subset (sync failures, short
     writes, latency, ENOSPC, lost watch changes) so a rare class is not drowned by a common one;
   - the crash points (after which op, or after how many completions);
   - the schedule: which actor (thread, process, the daemon or a reader) takes its next step;
   - the `Sim` seed (`tape.next_u64("sim seed")`), until `Sim` takes the tape itself.
3. **Run it in the simulation**: drive the core with the `Sim` driver, crash it, reopen it (the
   restart runs recovery exactly as the daemon would), and keep going.
4. **Check an oracle that states the invariant**, against a plain model kept beside the run, at
   every step and after every crash: "every row recorded and flushed appears exactly once after
   any crash", "a reader never sees a file the manifest does not list", "no byte is deleted while
   a pin holds it", "the bill equals the sum of the usage recorded, once". Assert what is
   true, not what the code happens to do.
5. **Planted-bug controls**: for each safeguard (the sync before the rename, the order of commit
   and consume, the second atomic), a test plants its removal (a test-only switch in the core)
   and expects the DST to find a counterexample within its case budget. An oracle that misses a
   plant is too weak; fix the oracle or the draws before trusting a green run. This is
   `test-the-cause` applied to the test itself.
6. **Replay a failure**: the report prints the least tape, its choices that are not calm by
   label, and the line that replays it (`BLAZE_SIM_TAPE='..'`). Pin it as a plain `#[test]`
   named for the property it broke, which gives that tape. It replays exactly because nothing
   in the run reads real time, real threads or hash order (`deterministic-output`); a case that
   does is reported as not a function of its tape.

A DST is fast enough for the merge gate at its default case count, and runs long
(`BLAZE_SIM_SEEDS`) in the release train.

### Worked example: blaze-profile's history

blaze-profile keeps a history on disk (docs/profiling.md): `manifest.json`, rewritten to a hidden
name and renamed over the last under `manifest.lock`, is the one commit point of a flush, a
merge and a retire (`crates/blaze-profile/src/history/manifest.rs`, `retire.rs`, `pin.rs`); and
the flight recorder's postmortem rings are mmapped, so a crashed daemon's last events survive
(`crates/blaze-profile/src/flight/postmortem.rs`). On 2026-11-04 a code review of this code, which
had landed with tests, found eight bug classes. None of its tests could have caught them, and
each maps to a DST capability that does:

| Bug class the review found | What catches it |
|---|---|
| No fsync of the new manifest (and its directory) before the rename: after a crash the name points at a torn or empty file | Crash points plus a rename that is durable before the data it names (the three-layer disk of sim.md; today's `Sim` keeps a completed whole-file write whole, so write it through appends and syncs to see it there) |
| A crash between the commit and its consumption (files listed, ring cursor not yet advanced) double-counts rows on restart | A crash point at every effect and the exactly-once oracle (today's `Sim::crash`) |
| A flush that fails part way (one table written, the next not) leaves a manifest naming half a flush | Swarm fault classes: `fail_one_in`, `fail_syncs`, short writes, ENOSPC (`fill`) |
| A DEBUG hold (data kept for a reader) is lost on a crash, and the data is deleted under it | Crash and restart with the oracle "nothing a live hold names is deleted" |
| Recovery runs on the writer's open but not on a read: a reader after a crash sees what a crash left | Draw a reader as its own actor after each crash, with the oracle on what it reads; several processes on one disk (sim.md) |
| Version skew on retired names: an older daemon reads the newer naming of retired files as live, or deletes them | Version skew, two builds' cores on one directory (today, both codecs in one test on one `Sim`) |
| A lost `flushed` update when a ring moves between two atomics: a writer's store lands between the mover's load and its store | A switch point at every atomic operation (`blaze-check`), plus what a crash keeps of a mapped ring (not modelled yet) |
| Recovery holds `manifest.lock` while it walks the directory, so a daemon that starts during it blocks | Multi-process restart on the virtual clock with a bounded-progress oracle: the second daemon's first answer arrives within its bound (`hold_lists`/`slow_writes` today; a second process once the disk holds several) |

Since 2026-11-04 the writer is a sans-IO core (`crates/blaze-profile/src/history/files.rs`,
marked `#![blaze::sans_io]`; `manifest.rs`, `retire.rs`, `compact.rs` and `merge.rs` too) driven
by `history/drive.rs`, and its DST is `history/files/tests.rs`: it draws flushes, build ends
(merges), crashes at a completion count and reopens (recovery), with swarm faults
(`fail_one_in`, `fill` for ENOSPC, `fail_syncs`, a held `manifest.lock`), and its oracle is that
after any crash and reopen the rows in listed files plus the rows recovered equal the rows
recorded, each once, no listed file is missing or torn, and the history always opens. Its
planted bugs (`files::Plant`) are the first two rows of the table: no sync before a rename, and
a flush's consumption marked after its commit.

The full DST for it draws records, flushes, merges, retires, pins, reads and restarts, crashes at any
point, and checks: every row recorded and flushed appears exactly once; no file a live pin's
generation lists is deleted; a reader opened after any crash sees only listed files; a restart
reaches its first answer within its bound. Each row of the table is a planted bug it must catch.

## Waits under the sandbox's filter

Every wait that reaches the real kernel (a new system call, a new driver, a pool or loop that
parks on one) gets one test that runs it in a process of its own under the build-script sandbox's
seccomp filter, marked as the sandbox launcher marks one, with a bound: list the case and call
`blaze_core::wait::filtered::{take_over, run}` (`crates/blaze-core/src/wait/filtered.rs`; its own
tests cover every public wait of `blaze_core::wait`, blaze-graph's `pool.rs` the workers' park), and
match on `Ended`, where a wait that does not end is `Ended::Hung` naming the case, never a hung
test. Its control is the same case not marked, which has to fail naming `io_uring_setup`. Linux
only: macOS's sandbox filters no system call by number and has one wait driver.

## Persisted state and causes

- `persisted-state-round-trips` (above): a restore equals a fresh build byte for byte; a DST adds
  the crashes.
- `test-the-cause` (above): remove the cause, watch the effect go. The method for finding a cause
  in the first place, from the profile, is the `debugging` skill.
